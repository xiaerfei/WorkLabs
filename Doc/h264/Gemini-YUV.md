# you asked

I420, YUV420p, NV12 有什么区别

---

# gemini response

这三个术语经常让初学者感到困惑，因为它们都属于 **YUV 4:2:0** 采样格式，但区别在于**数据在内存中的排列方式（布局）**。

在音视频开发中，理解这些布局是编写渲染（Metal/OpenGL）和编解码程序的基础。

---

### 1. 核心共同点：4:2:0 采样
无论是 I420 还是 NV12，它们都遵循 4:2:0 采样：
*   **含义：** 每 4 个亮度像素（Y）共用一组色度像素（U, V）。
*   **内存占用：** 每一个像素平均占用 $1.5$ 字节（12 bits）。
    *   计算公式：$Y + \frac{1}{4}U + \frac{1}{4}V = 1 + 0.25 + 0.25 = 1.5 \text{ bytes/pixel}$。

---

### 2. I420 (又称 YUV420p)
**I420** 是一种 **Planar（平面）** 格式。它将 Y、U、V 三个分量分别存储在三个独立的数组（平面）中。

*   **布局顺序：** 先存全部的 Y，再存全部的 U，最后存全部的 V。
*   **内存布局：** `YYYYYYYY UU VV`
*   **特点：** 结构非常直观，适合很多纯软件处理的算法。FFmpeg 内部默认处理的大多是这种格式。



---

### 3. NV12 (iOS/macOS 最常用)
**NV12** 是一种 **Semi-Planar（半平面）** 格式。它有两个平面：
1.  **Y 平面：** 存储全部的亮度信号。
2.  **UV 平面：** 存储色度信号，但 U 和 V 是**交错存储**的。

*   **布局顺序：** 先存全部的 Y，然后是一个 U 跟着一个 V。
*   **内存布局：** `YYYYYYYY UVUV`
*   **特点：** 这是 **iOS (Camera/VideoToolbox)** 和 **Intel/NVIDIA 硬解码**最喜欢的格式。
    *   **为什么 iOS 常用 NV12？** 在 GPU 渲染时，NV12 只需要两个纹理（Texture）：一个单通道的 Y 纹理和一个双通道的 UV 纹理。这比 I420 的三个纹理更节省内存访问开销。



---

### 4. 关键对比表

| 特性 | I420 (YUV420p) | NV12 |
| :--- | :--- | :--- |
| **类型** | 平面格式 (Planar) | 半平面格式 (Semi-Planar) |
| **平面数** | 3 个平面 (Y, U, V) | 2 个平面 (Y, UV) |
| **排列** | `YYYY... UUUU... VVVV...` | `YYYY... UVUVUV...` |
| **主要用途** | 软件编解码、FFmpeg 内部处理 | **iOS 原生采集/硬件加速渲染** |
| **对齐要求** | 各分量独立对齐 | Y 之后紧跟 UV 交错 |

---

### 5. 开发者视角：如何选？

作为 iOS 开发，你主要会遇到以下场景：
1.  **采集端：** 从 `AVCaptureVideoDataOutput` 拿到的通常是 **NV12**。如果你要直接传给 Metal 渲染，不需要转换，直接映射两个纹理即可。
2.  **处理端：** 如果你要用 FFmpeg 库做一些滤镜，FFmpeg 可能会要求你先转成 **I420**（使用 `sws_scale` 函数）。
3.  **渲染端：** 
    *   如果你用 **Metal**，建议直接支持 NV12，性能最好。
    *   如果你用 **OpenGL ES**，通常需要将 NV12 转换或使用扩展支持。

> **避坑指南：** 
> *   还有一个格式叫 **NV21**，它是安卓（Android）常用的，布局是 `YYYY... VUVU...`。它和 NV12 唯一的区别就是 U 和 V 的顺序反了。在 iOS 开发中，如果发现画面颜色发青或发红，通常就是 UV 顺序搞反了。

你想看看在 **Metal** 中如何分别加载 NV12 的两个平面来渲染出一张彩色图吗？

# gemini response

除了你提到的 4:2:0 系列，YUV 家族其实非常庞大。在音视频开发中，格式的选择主要取决于**压缩效率**与**处理性能**之间的权衡。

我们可以按照**采样比例**和**存储方式**两个维度来梳理：

---

### 1. 常见的采样比例 (Sampling)

采样比例决定了色彩的“细腻程度”。

*   **YUV 4:4:4：** 每个 Y 分量都有对应的 U 和 V。**无损**，色彩最精准，常用于高端后期制作或电脑显示器信号传输。
*   **YUV 4:2:2：** 每两个 Y 共用一组 UV。常见于**专业摄像机**和某些高质量视频编码（如 H.264 High 4:2:2 Profile）。
*   **YUV 4:2:0：** 每四个 Y 共用一组 UV（横向纵向各减半）。**最常用**，是互联网视频和移动端的工业标准。



---

### 2. 必须知道的常用格式

#### **A. YUY2 (又称 YUYV)**
*   **类型：** Packed（打包格式）。
*   **布局：** `Y0 U0 Y1 V0 Y2 U1 Y3 V1...`
*   **特点：** 它属于 **4:2:2** 采样。所有的 Y、U、V 都在**一个平面**里交叉存储。
*   **场景：** 很多 **USB 摄像头**默认输出的就是 YUY2 格式。因为它是打包存储，显卡或处理器在读取时非常快，不需要跨多个内存区域。

#### **B. NV21**
*   **类型：** Semi-Planar（半平面）。
*   **布局：** `YYYY... VUVU...`
*   **特点：** 和 NV12 简直是“孪生兄弟”，区别仅在于 UV 平面里是 **V 在前，U 在后**。
*   **场景：** **Android 平台的默认格式**。如果你做跨平台开发，处理摄像头数据时，iOS 看 NV12，Android 看 NV21。

#### **C. YV12**
*   **类型：** Planar（平面格式）。
*   **布局：** `YYYY... VVVV... UUUU...`
*   **特点：** 和 I420 (YUV420p) 只有一处不同——**U 和 V 的顺序反了**。
*   **场景：** 某些老旧的编解码器或特定图形库（如早期的 MPEG-4）会用到。

---

### 3. 高阶格式：10-bit 与 HDR
随着 35 岁的你开始研究 H.265 (HEVC) 和 HDR 视频，你会遇到更复杂的格式：

*   **P010：** 
    *   布局类似于 NV12，但它是 **10-bit** 的。
    *   **场景：** 它是 **HDR10** 视频在 Windows 和 iOS 硬件解码后的常见输出格式。每个分量占用 16 位内存（实际有效 10 位），处理起来比普通的 8-bit 格式复杂得多。

---

### 4. 总结与开发建议

| 格式名称 | 采样 | 存储方式 | 平面数 | 核心应用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **I420** | 4:2:0 | Planar | 3 | FFmpeg、软解、内核处理 |
| **NV12** | 4:2:0 | Semi-Planar | 2 | **iOS/macOS 原生渲染与硬解** |
| **NV21** | 4:2:0 | Semi-Planar | 2 | Android 原生开发 |
| **YUY2** | 4:2:2 | Packed | 1 | PC 端 USB 摄像头输出 |
| **P010** | 4:2:0 | Semi-Planar | 2 | **HDR 视频处理** |

---

### 💡 避坑锦囊 (iOS 开发视角)

1.  **颜色发绿/发紫？**
    通常是因为 **I420 和 YV12** 搞混了，或者是 **NV12 和 NV21** 搞混了（即 U 和 V 的位置对调了）。
2.  **画面出现重影或斜切？**
    这通常不是格式问题，而是 **Stride（跨距/对齐）** 问题。比如图片宽度是 1080，但为了内存对齐，系统给你的 Buffer 每行可能是 1088 字节。如果你按照 1080 去读取，画面就会错位。
3.  **Metal 渲染优化：**
    在 iOS 上用 Metal 渲染 YUV 时，最推荐的做法是利用 `CVMetalTextureCacheCreateTextureFromImage` 针对 NV12 的两个 Plane 分别创建纹理。

# gemini response

在音视频开发中，**4:2:0** 这种写法的专业术语叫 **“色度抽样”（Chroma Subsampling）**。

简单来说，它的核心逻辑是：**利用人眼对“亮度”极度敏感、对“颜色”相对迟钝的生理特性，在不显著影响视觉质量的前提下，把颜色信息丢掉一部分，从而大幅压缩数据量。**

为了理解这三个数字到底指代什么，我们需要先建立一个 **$4 \times 2$** 的像素矩阵模型。

---

### 1. 数字背后的含义：$J:a:b$

这种表示法通常写成 **$J:a:b$**：
*   **$J$**：参考块的宽度（通常固定为 **4** 个像素）。
*   **$a$**：**第一行**像素中，保留了多少组色度（U/V）信号。
*   **$b$**：**第二行**像素中，相对于第一行，**新增**了多少组色度信号。



---

### 2. 深度拆解 4:2:0

当我们说一个视频是 **4:2:0** 时，它的具体含义是：

1.  **$J=4$**：我们观察一个 4 像素宽、2 像素高的区域。
2.  **$a=2$**：第一行（4个像素）中，每 2 个亮度像素共用 1 组色度信号。所以 4 个像素只存 **2** 组颜色。
3.  **$b=0$**：第二行（4个像素）中，**完全不采样新的颜色**，而是直接复用第一行的颜色数据。

**直观理解：**
在 $2 \times 2 = 4$ 个像素的方阵里，只有左上角的那个像素拥有完整的颜色信息，剩下的 3 个像素都“蹭”它的颜色用，但它们各自保留自己的亮度（灰度）。

---

### 3. 各种抽样比例的对比

为了让你看清 4:2:0 到底有多狠，我们对比一下其他主流格式：

| 格式 | 颜色保留情况 | 压缩率 (相对于 4:4:4) | 应用场景 |
| :--- | :--- | :--- | :--- |
| **4:4:4** | 1:1，每个像素都有独立颜色 | 100% (无损) | 高端后期、电影特效、显示器信号 |
| **4:2:2** | 横向缩减，每 2 个像素共用颜色 | 66.7% | 专业摄像机、高质量 ProRes 编码 |
| **4:2:0** | **横向纵向都缩减**，每 4 个像素共用颜色 | **50%** | **几乎所有互联网视频、iOS/Android 视频、H.264/H.265** |

---

### 4. 为什么要用 4:2:0？（从 iOS 开发视角看）

如果你做过 iOS 的图形渲染，你会发现原生的图像通常是 **RGBA8888**。
*   一个 1080p 的像素：$R(1) + G(1) + B(1) + A(1) = 4$ 字节。
*   转成 **YUV 4:2:0** 后：平均每个像素只占 **1.5** 字节。

**节省了 62.5% 的空间！**

这对于移动端来说意义重大：
1.  **带宽：** 直播推流时，传输 4:2:0 只需要不到一半的带宽。
2.  **内存：** 在 Mac mini M4 上处理 4K 视频流时，4:2:0 能极大地减轻内存总线的压力。
3.  **硬件加速：** Apple 的 **VideoToolbox** 硬件解码器对 4:2:0（尤其是 NV12 布局）做了极致优化。

---

### 5. 总结：一个极简的口诀

*   **4:4:4**：大家都有色（全彩）。
*   **4:2:2**：左右邻居共用色（横向减半）。
*   **4:2:0**：**上下左右四邻居共用色**（横向纵向全减半）。

# gemini response

这是一个非常棒的观察！这直戳音视频处理中**“空间相关性”**的核心。

简单来说，**4:2:0 采样不是按“行”来分的，而是按“块（Block）”来分的。**

### 1. 为什么不能只让第一行共用？
如果你让 `Y1 | Y2 | Y3 | Y4` 共用 `U1 | V1`，这在图形学上叫做** 1D（一维）采样**。
*   **后果：** 你的水平颜色分辨率虽然降低了，但垂直方向（纵向）还是全分辨率。
*   **问题：** 现实世界的物体（比如人的脸、树木）在空间上是**上下左右**都具有相似颜色的。

### 2. “田字格”逻辑（2x2 像素块）
4:2:0 的设计初衷是为了在**水平和垂直两个维度上同时节省空间**。

想象一个 $2 \times 2$ 的“田字格”：
```text
(第一行)  Y1  Y2
(第二行)  Y5  Y6
```
在这个小方块里，人眼很难察觉到这四个点其实用的是同一个颜色（UV）。

*   **如果按你的设想（横向 4 个共用）：** 你的色彩在水平方向被砍掉了 75%，但纵向没砍。这会导致画面出现明显的**色边**（水平方向模糊，纵向尖锐），视觉上非常不和谐。
*   **4:2:0 的方案：** 水平砍 50%，纵向也砍 50%。这种**对称的模糊**反而更符合人眼的视觉特征，看起来更自然。



---

### 3. 内存布局的“欺骗性”
你看到的内存排列是：`Y1 Y2 Y3 Y4 Y5 Y6 Y7 Y8`。这只是因为内存是**一维线性**的，它不得不把二维的图像“压平”存储。

但实际上，解码器在读取这串数据时，脑子里是有“宽度”这个概念的：

1.  它读取第一行的 `Y1, Y2`。
2.  它根据图像宽度，跳到第二行读取 `Y5, Y6`。
3.  **它去 U 平面取走 1 个字节的 U1，去 V 平面取走 1 个字节的 V1。**
4.  然后把这 4 个 Y 和 1 组 UV 丢进着色器，渲染出 4 个彩色像素。

---

### 4. 工程实战中的“巨坑”：Stride（跨距）
既然你提到了内存排列，作为 35 岁的资深开发，你必须掌握这个**让无数新手抓狂的细节**。

假设你的视频宽度是 **7**（奇数）：
*   **逻辑上：** 宽度是 7，所以一行应该存 7 个 Y。
*   **实际上：** 为了内存访问效率（CPU 喜欢 16 或 32 字节对齐），系统会在第 7 个 Y 后面偷偷补上 1 个无意义的字节，让它变成 8。



**这时候如果你还是按“宽度为 7”去内存里找第二行的 Y5，你会发现找错了位置！** 因为你漏算了那个补齐的字节。
*   **现象：** 画面会发生严重的“斜切”或者出现绿边。
*   **解决：** 在处理 iOS 的 `CVPixelBuffer` 时，永远不要直接用 `width`，而要用 `CVPixelBufferGetBytesPerRow`。

---

### 5. 总结
4:2:0 选择 **$2 \times 2$ 方阵** 而不是 **$1 \times 4$ 长条**，是因为：
1.  **更平衡：** 横向纵向压缩比一致。
2.  **更高效：** 符合二维图像的空间局部性。
3.  **更美观：** 颜色过渡在两个轴向上都相对平滑。

你画的那个矩阵：
```text
Y1 | Y2 | U1/V1
Y5 | Y6 | (共用)
```
这才是音视频底层逻辑的真实写照。

### 1. 跨距 (Stride / Linesize) 与内存对齐
这是新手最容易踩的坑。
*   **现象：** 你计算的 Buffer 大小是 $Width \times Height \times 1.5$，但渲染出来的画面却是歪的，或者满屏斜纹。
*   **原理：** 为了提高 CPU/GPU 的内存读取速度，每一行数据在内存中通常需要 **16 或 32 字节对齐**。
*   **计算公式：** `Stride = Width + Padding`。
*   **工程建议：** 在使用 FFmpeg 时，永远用 `frame->linesize[0]` 而不是 `width`；在 iOS 中用 `CVPixelBufferGetBytesPerRow`。


---

### 2. 颜色空间与转换矩阵 (BT.601 vs BT.709 vs BT.2020)
当你把 YUV 转回 RGB 渲染到屏幕上时，公式并不是唯一的。如果你发现视频颜色偏淡或发红，通常是选错了转换矩阵。
*   **BT.601 (SD)：** 标准清晰度（标清）视频使用的标准。
*   **BT.709 (HD)：** 高清（1080p）视频最常用的标准。
*   **BT.2020 (UHD)：** 4K/8K 及 HDR 视频使用的标准，色彩范围（色域）广得多。
*   **转换公式示例（BT.709）：**
$$
\begin{bmatrix} R \\ G \\ B \end{bmatrix} = \begin{bmatrix} 1 & 0 & 1.5748 \\ 1 & -0.1873 & -0.4681 \\ 1 & 1.8556 & 0 \end{bmatrix} \begin{bmatrix} Y \\ U - 128 \\ V - 128 \end{bmatrix}
$$

---

### 3. 数值范围 (Full Range vs Limited Range)
这是另一个“颜色看起来不对劲”的罪魁祸首。
*   **Limited Range (MPEG Range)：** 为了防止信号干扰，Y 的取值范围是 **16-235**，UV 是 **16-240**。这是大多数广播级和在线视频的标准。
*   **Full Range (JPEG Range)：** 取值范围是 **0-255**。通常用于相机拍照或电脑桌面采集。
*   **常见 Bug：** 如果你把 Limited Range 的视频当成 Full Range 来渲染，你会发现**黑色不黑（发灰），白色不亮（发污）**。

---

### 4. 4:2:0 的“变种”：NV12 vs I420 vs NV21
正如之前讨论的，这只是内存布局的不同：
*   **Planar (I420/YV12)：** Y、U、V 各占一个连续平面。
*   **Semi-Planar (NV12/NV21)：** Y 占一个平面，UV/VU 交错占一个平面。
*   **工程价值：** 现代移动端芯片（A系列、骁龙）的硬解码器通常直接输出 **NV12**。如果你要把 FFmpeg 的 I420 传给 iOS 的硬件渲染，需要一次 `libyuv` 转换。

---

### 5. 采样中心对齐 (Chroma Siting)
这是一个很细的知识点：色度像素（U/V）到底对应哪一个亮度像素（Y）的中心？
*   **MPEG-2 / H.264 标准：** 色度采样点在水平方向上和第一个 Y 像素对齐，但垂直方向在两个 Y 之间。
*   **JPEG 标准：** 色度采样点在四个 Y 像素的正中心。
*   **后果：** 如果对齐方式不对，在文字边缘或高对比度边缘会出现细微的彩色重影（Chroma Ghosting）。

# gemini response

计算 Buffer 大小时，最容易犯的错误就是直接用 $1920 \times 1080 \times 1.5$。在实际工程中，你必须考虑**内存对齐（Alignment）**带来的额外空间。

这里有两套计算逻辑：一种是**理想理论值**，另一种是**工程实际值**。

---

### 1. 理想理论值（不含对齐）
这是文件存储或网络传输时的大小（为了省空间，通常不包含填充位）。

**以 YUV 4:2:0 为例：**
*   **Y 分量：** $1920 \times 1080 = 2,073,600$ 字节
*   **U 分量：** $(1920 / 2) \times (1080 / 2) = 1920 \times 1080 / 4 = 518,400$ 字节
*   **V 分量：** $(1920 / 2) \times (1080 / 2) = 518,400$ 字节
*   **总计：** $2,073,600 + 518,400 + 518,400 = 3,110,400$ 字节（约 **2.97 MB**）。

---

### 2. 工程实际值（包含 Stride / 对齐）
在 iOS 或 C++ 内存处理中，为了提高 CPU 读取效率（SSE/AVX指令集），每一行的末尾通常会填充一些无效字节。

**核心公式：**
$$Buffer\_Size = (Stride_Y \times Height) + (Stride_U \times Height / 2) + (Stride_V \times Height / 2)$$

#### 场景：假设系统要求 32 字节对齐
对于 1080p（宽 1920）：
*   $1920 / 32 = 60$（刚好整除），此时 $Stride = 1920$，无填充。
*   但如果是 **720p (1280x720)** 且宽度变为 **1270**：
    *   $1270$ 不能被 $32$ 整除。
    *   $Stride = ((1270 + 31) / 32) \times 32 = 1280$。
    *   每一行多出了 $10$ 字节的无用数据（Padding）。

---

### 3. 不同布局的具体计算

#### **A. I420 (Planar)**
这是三个独立的 Plane：
1.  **Y-Plane:** `Stride_Y * Height`
2.  **U-Plane:** `Stride_U * (Height / 2)`
3.  **V-Plane:** `Stride_V * (Height / 2)`
> *注意：$Stride_U$ 通常是 $Stride_Y / 2$。*

#### **B. NV12 (Semi-Planar, iOS 常用)**
这是两个 Plane：
1.  **Y-Plane:** `Stride_Y * Height`
2.  **UV-Plane:** `Stride_UV * (Height / 2)`
> *注意：在 NV12 中，虽然宽减半了，但因为 U 和 V 交错存储，所以 $Stride_{UV}$ 通常等于 $Stride_Y$。*

### 4. 代码实操 (C++ / iOS)

在 35 岁的职场实战中，千万不要手写 1920 这样的数字，要学会调用系统接口。

#### **iOS (Objective-C/Swift) 获取方式：**
```objectivec
// 假设 pixelBuffer 是 CVPixelBufferRef
size_t strideY = CVPixelBufferGetBytesPerRowOfPlane(pixelBuffer, 0);
size_t strideUV = CVPixelBufferGetBytesPerRowOfPlane(pixelBuffer, 1);
size_t height = CVPixelBufferGetHeight(pixelBuffer);

// 正确的总大小
size_t totalSize = strideY * height + strideUV * (height / 2);
```

#### **FFmpeg (C++) 获取方式：**
```cpp
// 假设 frame 是 AVFrame*
int total_size = 0;
for (int i = 0; i < 3; i++) {
    // frame->linesize[i] 就是 Stride
    // 对于 YUV420P，i=0 是 Y，i=1,2 是 U, V
    total_size += frame->linesize[i] * (i == 0 ? frame->height : frame->height / 2);
}
```

### 5. 总结：为什么这个计算对你很重要？

如果你在做 **OBS 移植** 或者 **WebRTC 优化**：
1.  **内存拷贝（memcpy）：** 如果你不知道 Stride，直接用 `memcpy(dst, src, width * height)`，画面就会**错位（每行错开几个像素）**。正确做法是**按行拷贝**，循环 `height` 次。
2.  **GPU 纹理映射：** 在 Metal 中创建纹理时，必须传入正确的 `bytesPerRow`。如果传错了，GPU 会解析到错误的内存地址，导致**画面花屏**。

**避坑小贴士：**
当你在 M4 Mac 上测试 1080p 视频时，通常 Stride 刚好等于 Width（因为 1920 是 64 的倍数）。这很容易让你产生“Stride 没用”的错觉。**建议你找一个奇数宽度的视频（比如 1081x1920）进行测试**，那时 Stride 的作用会立刻显现出来。
