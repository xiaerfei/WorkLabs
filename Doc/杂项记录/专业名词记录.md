# 音视频专业名词记录

## FEC — 前向纠错（Forward Error Correction）

> 参考：[音视频协议--FEC - 知乎](https://zhuanlan.zhihu.com/p/164364436)（作者 Fenngtun，MediaStack 专栏）

---

### 1. 背景与动机

基于 IP 网络的多媒体通信系统（比如 WebRTC）中，网络丢包对多媒体通信质量有非常严重的影响：
- **视频**：马赛克、图像模糊、帧率下降等
- **音频**：声音失真、噪声干扰、音频中断等

WebRTC 主要采取两种手段对抗网络丢包：

| 手段 | 原理 | 特点 |
|------|------|------|
| **NACK（丢包重传）** | 接收端检测到丢包后请求重传 | 需要 RTT 往返时间，高延迟下体验差 |
| **FEC（前向纠错）** | 发送端附带冗余纠错码，接收端自行恢复 | 无需等待重传，低延迟；但额外占用带宽 |

---

### 2. WebRTC FEC 概述

WebRTC 中的 FEC 分为两个部分：

- **UlpFEC**：基于 RFC 5109，使用 RED 封装，是最常用的方案
- **FlexFEC**：基于 RFC draft-ietf-payload-flexible-fec-scheme，更灵活

FEC 对 RTCP 统计透明，冗余度由丢包情况和 BWE（带宽估计）动态决定，内部维护静态冗余度表。**冗余度范围：0 — 255**（255 相当于 100% 冗余度）。

#### 冗余度计算

```
冗余比例 N：N 个媒体包生成 1 个 FEC 包
冗余度 = FEC 个数 / (FEC 个数 + 媒体包个数)
```

#### 随机丢包率与恢复率关系

FEC 使用异或（XOR）算法。假设媒体包:FEC包 = 5:1，则每 5 个媒体包 + 1 个 FEC 包组成一个 **FEC Group**，客户端可在该 Group 内利用 FEC 恢复丢失的媒体包。

### 3. ULPFEC 理论基础（RFC 5109）

ULPFEC 全称 **Uneven Level Protection FEC**（非均等保护前向纠错），能对不同重要程度的数据包提供不同级别的保护。

#### 3.1 核心概念

- FEC 包中设置 **基准序列号 N**，偏移量掩码 m(k) 的第 i 位为 1 时，表示序列号为 N+i 的媒体包在本 FEC 包的第 k 级别受保护
- 第 k 级别的保护数据大小由 L(k) 指示
- **非均等保护**：重要数据部分分配更多保护（更多 FEC 包），次要部分分配较少保护，充分利用带宽

#### 3.2 ULPFEC 报文格式

```
┌──────────────┐
│  RTP Header   │  仅在独立流发送时使用（RFC 3550）
├──────────────┤
│  FEC Header   │  10 字节
│  - E flag     │  扩展位（当前为 0）
│  - L flag     │  长偏移掩码标志（0=16bit, 1=48bit）
│  - P/X/CC/M/PT│  由受保护的所有媒体包对应字段 XOR 得到
│  - SN base    │  受保护媒体包的最小序列号
│  - TS recovery│  受保护媒体包 Timestamp XOR 结果
│  - Length rec │  受保护媒体包负载长度 XOR 结果
├──────────────┤
│ Level 0 Head  │  4 或 8 字节（取决于 E flag）
│  - Prot len   │  2 字节，本级别保护长度
│  - Mask       │  2 或 6 字节，偏移掩码
│ Level 0 Payload│
├──────────────┤
│ Level 1 Head  │
│ Level 1 Payload│
├──────────────┤
│     ...       │  可多个 Level
└──────────────┘
```

#### 3.3 FEC 头部构造

FEC 头部本质上是**所有受保护 RTP 包头部 XOR 运算**的结果：
- 前 8 字节：与 RTP 头部前 8 字节格式相同，数据来自媒体包 XOR
- 后 2 字节（length recovery）：媒体包 RTP 负载长度的 XOR
- FEC 只保护 RTP 头部前 12 字节，CSRC 和 RTP Extensions 视为负载部分保护

保护级别负载 = 本级别保护的所有媒体数据包对应部分逐字节 XOR

#### 3.4 报文发送方式

ULPFEC 报文有两种发送方式：
1. 使用独立的 RTP 流发送
2. **封装在 RED 报文中随源媒体数据一起发送（WebRTC 采用此方式）**

**RED（Redundant Coding）** 定义在 RFC 2198，是对 RTP 负载数据的二次封装。RED 有两种数据块格式：
- **Primary Data Block**：F 标志位（是否还有后续 Block）、block PT、timestamp offset、block length
- **Redundant Data Block**：同上结构，支持多层冗余

发送流程：FEC 包 → 封装为 RED → 封装为 RTP → 发送

#### 3.5 报文恢复

报文恢复即构造的逆过程，分为两步：

1. **确定恢复集合**：确定恢复丢失媒体包所需的 FEC 包和未丢失媒体包的集合
2. **重建数据包**：
   - **重建 RTP 头部**：FEC 包前 10 字节与已收媒体包前 10 字节 XOR → 恢复 RTP 头部
   - **重建 RTP 负载**：对各保护级别分别执行 XOR 恢复，逐级还原完整负载

### 4. ULPFEC 在 WebRTC 中的实现

#### 4.1 FEC 报文构建

控制流程：编码后处理 → PayloadRouter → RtpSenderVideo::SendVideo() → SendVideoPacketAsRedMaybeWithUlpfec()

核心函数 **ForwardErrorCorrection::EncodeFec()** 流程：

```
EncodeFec(media_packets, protection_factor, num_important_packets,
          use_unequal_protection, fec_mask_type, fec_packets)
{
    // Step 1: 根据 media_packets 数量和 protection_factor 确定 FEC 包数
    num_fec = m * factor / 256

    // Step 2: 构建掩码表，获取 FEC 包所需掩码
    // 关键步骤 —— packet_masks_ 决定媒体包在 FEC 包中的保护分布

    // Step 3: 生成 FEC 包（半成品头部 + 成型负载）
    GenerateFecPayloads(media_packets, num_fec_packets)

    // Step 4: 填充并修正 FEC 头部
    FinalizeFecHeaders(num_fec_packets, media_ssrc, seq_num_base)
}
```

> **注意**：WebRTC 仅使用 Level 0 保护，内部将保护 RTP 头部的 FEC 头部称为 Level 0，保护 RTP 负载的 FEC Level 称为 Level 1（与 RFC 5109 定义稍有不同）。

#### 4.2 掩码表与掩码策略

用 m × n 零一矩阵描述保护分布：`m[i][j]=1` 表示第 i 个媒体包受第 j 个 FEC 包保护。

两种丢包模型对应的掩码表：
- **kPacketMaskRandomTbl**：随机丢包场景
- **kPacketMaskBurstyTbl**：突发丢包场景

**非均匀保护三种模式**（m 个媒体包，前 k 个为重要包，分配 t 个 FEC 包）：

| 模式 | 策略 | 掩码确定方式 |
|------|------|-------------|
| **kModeNoOverlay** | 非叠加保护 | `mask_table[k][t]` 和 `mask_table[m-k][n-t]` 移位组合 |
| **kModeOverlay** | 叠加保护 | `mask_table[k][t]` 和 `mask_table[m][n-t]` 拼接 |
| **kModeBiasFirstPacket** | 均匀保护 + 首包加强 | `mask_table[m][n]`，第一列全部置 1 |

#### 4.3 报文接收与丢包恢复

接收流程：

```
RTP 包到达 → RtpStreamReceiver::ReceivePacket()
    → 判断为 RED 包 → ParseAndHandleEncapsulatingHeader()
        → RED 解包（去 RED 头部，得纯 RTP/FEC 报文）
        → UlpfecReceiver 处理

ProcessReceivedFec():
    1. 若是 RTP 包 → OnRecoveredPacket() 发送到 VCM（不耽误解码）
    2. DecodeFec() 执行恢复
    3. 将恢复包送 VCM 解码

DecodeFec():
    - FEC 包 → Fec 列表  + 遍历 Media 列表关联保护关系
    - RTP 包 → Media 列表 + 遍历 Fec 列表建立反向关联
    - AttemptRecovery(): 遍历 Fec 列表，丢包数 == 1 时调用 RecoveryPacket()

RecoveryPacket():
    1. 准备：将 FEC 包头部+payload 拷贝到 recover_packet
    2. 恢复：对每个已收 RTP 包执行 XOR（结果存回 recover_packet）
    3. 收尾：修正 RTP 头部 → 得到最终恢复的 RTP 包
```

**关键约束**：AttemptRecovery 只在 FEC Group 内恰好丢失 1 个包时才能恢复（XOR 算法的限制）。

### 5. 常见 FEC 策略对比

| 类型 | 算法基础 | 特点 | 适用场景 |
|------|----------|------|----------|
| **ULP FEC** | XOR + 非均等保护 | 低开销，支持按重要程度分级保护 | WebRTC 默认方案 |
| **RS FEC** | Reed-Solomon 多项式 | 纠错能力更强，可容忍多个丢包 | 丢包率高的信道 |
| **FlexFEC** | 灵活配置 | 支持动态参数配置，更灵活 | WebRTC 可选方案 |
