# 滤镜（颜色校正 / 裁剪）渲染问题排查

> 对应 [someissues.md](someissues.md) 记录的三条现象。本文是**排查纪要 + 根因假设 + 修法建议**，供复现后对照定位。
> 状态：✅ **已修复并实测通过（2026-06-15 核对）**。实际根因是 **10-bit HEVC 源被当成 8-bit BGRA 绑定纹理**——`5d8ecd2` 修「渲染分裂成左右两半」、`a75447c` 修「偏色/偏暗」（删 `is10Bit` 分支，P010 高位对齐可复用 8-bit 公式）。下文基于纯代码静态分析的根因假设（bytesPerRow 对齐 / 颜色附件等）仅部分命中，保留供回溯。

---

## 0. 现象（someissues.md 原文）

1. 修改**颜色矫正**或**裁剪**时，渲染的视图**总会分成左右两个部分**。
2. **裁剪**时，**颜色也不对**了。
3. 颜色矫正（如滑动亮度），**再次归零**时，颜色不正常。

三条都发生在**滤镜激活**（`WLBasicVideoFilter.isIdentity == NO`，走 Metal 离屏渲染）时；滤镜全默认值时透传原帧，一切正常。

---

## 1. 关键背景：管线与数据格式（已核实）

### 源像素格式
- **摄像头** `WLCameraSource`：`kCVPixelFormatType_420YpCbCr8BiPlanarVideoRange`（NV12，**video range**）。
  - `WLCameraSource.m:77`
- **视频文件** `WLMediaSource`：解码后经 `sws_scale` 转 `kCVPixelFormatType_32BGRA`（BGRA）。
  - `WLMediaSource.m:485-487`、`sws_scale` 用 `CVPixelBufferGetBytesPerRow` 取 dstStride（`WLMediaSource.m:492-497`，stride 正确）

### 滤镜路径 `WLBasicVideoFilter`（`Filter/WLBasicVideoFilter.m`）
- `isIdentity` 时透传（retain 原帧返回，零 GPU）。
- 否则：Metal 离屏渲染一遍过 → 输出到**自有 pool 的 BGRA buffer**。
- **裁剪会改变输出尺寸**：`outW = inW*(1-cropL-cropR)`，再量化到 16 的倍数（`WLBasicVideoFilter.m:131-147`）。注释明言「裁剪改变输出尺寸（与原 CoreImage 语义一致）」。
- 输出 pool 属性：BGRA + IOSurface + Metal 兼容，**未设颜色附件、未设 bytesPerRow 对齐**（`WLBasicVideoFilter.m:210-230`）。

### 输出消费端
- 滤镜输出 `toFork` 被 fork 到两路（`WLStreamsManager.m:332-349`）：
  1. **预览**：每路源一个 `WLStreamPreview`（`AVSampleBufferDisplayLayer` 叠加层）。
  2. **合成** `WLVideoMix`：进缓冲、tick 选帧、合成到画布 buffer → 仅给**编码器**（录制/推流），**不进实时预览**（`WLStreamViewController.m:222-225`）。
- 即：用户在画布上看到的「渲染视图」= 各源 `WLStreamPreview` 叠层，**不是**合成结果。合成结果只在 mp4 / 推流里。

### Shader（`Source/MediaFile/WLMetalPreviewShaders.metal`）
- `vertexShader`：全屏 / 定位 quad，texCoord 含 v-flip。
- `fragmentShader`：合成器用，YUV→RGB。
- `filterFragment`：滤镜用，镜像 / 裁剪 remap uv → YUV→RGB → 颜色校正（饱和度→对比度→亮度，luma 用 Rec.709）→ 色相 YIQ 旋转。
- **YUV→RGB 系数（重要，纠正常见误判）**：
  - **video-range 分支**（`filterFragment` 第 79-84 行 / `fragmentShader` 第 37-41 行）用的是 `1.164 / 1.793 / 0.213 / 0.533 / 2.115` —— 这是 **BT.709 video-range** 系数，**矩阵正确**。
  - full-range 分支用 `1.402 / 0.344 / 0.714 / 1.772` —— BT.601 full-range。但**摄像头是 video range、视频文件是 BGRA（非 YUV）**，full-range YUV 分支**几乎不会被命中**。
  - 结论：**摄像头走的是 709 video-range，矩阵不是问题**（曾怀疑 601/709 不匹配，核实后排除）。

## 2. 逐条根因假设

### 现象 3 / 现象 2 的颜色部分 —— 颜色不正常

**最可能根因：滤镜输出的 BGRA buffer 没有颜色附件（color attachments）。**

- 透传（滤镜关）时：预览拿到的是**带完整颜色标签**的 NV12（摄像头采集帧自带 primaries / transfer / matrix），`AVSampleBufferDisplayLayer` 按标签做色彩管理 → 显示正确。
- 滤镜开时：shader 用 709 矩阵把 YUV 转成 gamma 编码的 RGB（值本身正确），写进 pool 的 BGRA buffer，但该 buffer **无任何颜色附件**（`WLBasicVideoFilter.m:213-219` 只设了 format/宽高/Metal/IOSurface）。`AVSampleBufferDisplayLayer` 只能**猜**它的色彩空间。
- 不同显示器（内置 P3 vs 外接 sRGB/其它配置）猜测结果不同 → **同一份数据偏色程度因屏而异**。这与「换机/换屏后表现不一致」高度吻合（见文末复现条件）。

**为什么现象 3「归零后仍不正常」**：亮度滑块拖回「0」时多半不是精确 `0.0f`（float），`isIdentity` 仍为 `NO` → 滤镜仍激活 → 仍输出无附件 BGRA → 偏色不消失，用户感知为「我归零了颜色还是不对」。
- `isIdentity` 判定：`WLBasicVideoFilter.m:73-79`（`brightness == 0.0f` 等浮点等值比较）。

**现象 2「裁剪时颜色也不对」**：裁剪同样让滤镜激活、输出无附件 BGRA → 与上同源，不是裁剪独有的颜色 bug。

**置信度**：中高。颜色路径矩阵正确，差异基本只剩「输出 buffer 无颜色附件」这一项；且与设备/显示器相关性吻合。

---

### 现象 1 —— 渲染视图「分成左右两个部分」

**已确定的几何成因（裁剪方向）：裁剪改变 buffer 宽高比，但预览浮层与合成 layout 都不跟随。**

- 预览浮层 `WLStreamPreview` 的 frame 只在**首帧**按 buffer 宽高比适配一次（`aspectInitialized`，`WLStreamPreview.m:181-194`），之后固定。
- `videoGravity = AVLayerVideoGravityResizeAspect`（`WLStreamPreview.m:87`）。
- 裁剪后 buffer 变窄（裁左右）→ 装进偏宽的旧浮层 → **左右黑边（pillarbox）**＝「分成左右两个部分」。裁上下则是上下黑边（letterbox）。
- 合成侧 `WLVideoMix` 把源 buffer **拉伸填充**到固定 layout rect（`WLVideoMix.m` 各源 quad 按 layout→NDC，不保宽高比）→ mp4 里表现为**拉伸变形**而非黑边。
- 即：预览（保比黑边）与合成（拉伸填充）对裁剪后帧的处理**本就不一致**；未裁剪时因首帧把浮层 frame 设成了 buffer 宽高比，两者恰好一致，才看不出来。

**未解释的部分：单纯颜色校正（不裁剪）为何也会「左右分裂」。**
- 颜色校正**不改变输出尺寸**（`outW==inW`，标准分辨率下量化也不变），理论上不该产生黑边/分裂。
- 纯代码层面**未找到** shader 几何错误：quad、texCoord、`WLFilterParams` 结构体布局（全 4 字节标量，C 与 Metal 一致）、输入/输出纹理绑定（都走 IOSurface，stride 由 CVMetalTextureCache 保证一致）均正确。预览经 IOSurface 显示，理论上不会因 stride 错位分裂。
- 该现象**随设备/显示器变化**，故强烈怀疑与**外接显示器的分辨率 / HiDPI 缩放 / backing scale** 相关，而非算法 —— 但**尚无定论**，需复现时实拍确认。

**置信度**：裁剪方向的黑边/拉伸＝高；颜色校正也分裂＝未知，待实测。

## 3. 修法建议（按优先级）

### A. 给滤镜 / 合成输出 buffer 补颜色附件（修颜色，低风险，原理正确）
- 在 `WLBasicVideoFilter` 拿到输出 `dst` 后，`CVBufferPropagateAttachments(input, dst)`，把源的 709 色彩标签透传到输出 BGRA。
- 合成画布输出（`WLVideoMix` 的 pool buffer）显式打 709 标签（primaries/transfer = `ITU_R_709_2`），与录制器声明的 BT.709 一致。
- 预期：预览开滤镜的颜色 == 关滤镜，且不再因屏而异。**无论哪台机都该做。**

### B. 统一裁剪后的「预览 vs 合成」几何（修分裂/拉伸）
有几种语义，需产品决策（之前已向用户提出，待定）：
1. **Trim + 源框跟随裁剪比例收缩**（OBS 式，最符合直觉，改动最大）：浮层 frame 与 mix layout 随裁剪后内容比例变化，内容不变形。需裁剪比例流到 layout（多文件改动）。
2. **裁掉的边变透明、内容保持原位原尺寸**（改动小，仅 filter+shader）：输出尺寸 = 输入尺寸，被裁区域 alpha=0。但裁某一侧时该侧会显示透明/黑，用户可能仍觉得「分裂」。
3. **预览也改拉伸填充**（`videoGravity = Resize`，改动最小）：去黑边，但裁剪后画面会和合成一样被拉伸变形。

> 注：本质矛盾——裁剪改变内容宽高比，要在固定宽高比的框里**不变形**显示，必然要么有边（黑/透明）、要么改框的宽高比。没有「既不变形又无边又不改框」的解。

### C. 待实测后再定：颜色校正「左右分裂」与外接屏的关系
- 复现时优先确认是显示链路（预览）还是数据本身（mp4），再决定是否还有第二个几何 bug。

## 6. 已尝试修复（2026-06-10，Mac mini + 外接显示器实测）

> 在 Mac mini M4 + 外接显示器上实测，Enable macOS HiDPI。共 8 处改动，**颜色问题可能已修复（仅待对比确认），「左右分裂」问题未知**（第 7、8 条尚未实测）。

### 尝试 1：滤镜输出 buffer 补颜色附件 ✅ 已合入

`WLBasicVideoFilter.m` — `processVideoFrame:` 获取 dst 后添加：

```objc
CVBufferPropagateAttachments(pixelBuffer, dst);
```

把源帧的 BT.709 色彩标签（primaries/transfer）透传到输出 BGRA buffer，使 `AVSampleBufferDisplayLayer` 不再猜测色彩空间。

**结果**：颜色问题可能改善（待对比确认），但左右分裂依旧。

### 尝试 2：isIdentity 改用阈值比较 ✅ 已合入

`WLBasicVideoFilter.m:73-83` — 浮点精确比较改为阈值：

```objc
static const float kEps = 0.001f;
fabsf(self.brightness) < kEps  // 替代 self.brightness == 0.0f
```

**结果**：逻辑正确，归零后应能正确切回透传路径。

### 尝试 3：合成画布输出补 BT.709 颜色标签 ✅ 已合入

`WLVideoMix.m` — `renderComposite:` 获取输出 buffer 后添加：

```objc
CVBufferSetAttachment(out, kCVImageBufferColorPrimariesKey, ...);
CVBufferSetAttachment(out, kCVImageBufferTransferFunctionKey, ...);
CVBufferSetAttachment(out, kCVImageBufferYCbCrMatrixKey, ...);
```

**结果**：合成输出色彩管理正确。

### 尝试 4：contentsScale 对齐屏幕缩放因子 ❌ 无效

`WLStreamPreview.m` — `makeBackingLayer` 中设置：

```objc
_displayLayer.contentsScale = [NSScreen mainScreen].backingScaleFactor ?: 2.0;
```

加 `viewDidMoveToWindow` 动态更新。

**结果**：仅影响渲染分辨率（Retina 屏更清晰），**不是左右分裂的根因**。

### 尝试 5：显式 stride 对齐 ❌ 无效

`WLBasicVideoFilter.m` + `WLVideoMix.m` — pool 属性添加：

```objc
(id)kCVPixelBufferBytesPerRowAlignmentKey: @(4)
```

**结果**：stride 对齐不是根因。

### 尝试 6：去掉 IOSurface ❌ 无效

`WLBasicVideoFilter.m` — pool 属性移除 `kCVPixelBufferIOSurfacePropertiesKey`，仅保留 `kCVPixelBufferMetalCompatibilityKey`。

**结果**：`CVMetalTextureCache` 支持非 IOSurface 的 CVPixelBuffer（macOS 10.13+），但左右分裂依旧。

### 尝试 7：去除 YCbCrMatrix 传染 ❌ 已验证无效

`WLBasicVideoFilter.m` — `CVBufferPropagateAttachments` 后追加：

```objc
CVBufferRemoveAttachment(dst, kCVImageBufferYCbCrMatrixKey);
```

**理论**：`CVBufferPropagateAttachments` 把源 NV12 的 YCbCrMatrix 传染给了 BGRA 输出。`AVSampleBufferDisplayLayer` 见到 RGB buffer 上有 YCbCrMatrix，可能误判为 YUV 再解码一次 → 画面分裂。实际上 kCVImageBufferYCbCrMatrixKey 对 RGB 格式应被忽略。

**结果**：❌ 无效。显示层不会为 RGB 格式应用 YCbCrMatrix，此键仅对 YUV 格式生效。

### 尝试 8：sublayer 模式（代替 makeBackingLayer）⏳ 待实测

`WLStreamPreview.m` — 移除 `makeBackingLayer` 重写，改为在 `setupLayer` 中将 `AVSampleBufferDisplayLayer` 作为 sublayer 添加到常规 NSView 的 backing layer 中：

```objc
// 改为 sublayer 模式
_displayLayer = [AVSampleBufferDisplayLayer layer];
_displayLayer.videoGravity = AVLayerVideoGravityResizeAspect;
_displayLayer.contentsScale = [NSScreen mainScreen].backingScaleFactor ?: 2.0;
_displayLayer.frame = self.layer.bounds;
_displayLayer.autoresizingMask = kCALayerWidthSizable | kCALayerHeightSizable;
[self.layer addSublayer:_displayLayer];
```

**理论**：
- 原 `makeBackingLayer` 让 `AVSampleBufferDisplayLayer` 成为视图的**主 backing layer**，HiDPI 下 view system 可能对它做额外的重采样/复合操作
- 其他 App（OBS、QuickTime Player 等）均使用 sublayer 模式
- sublayer 模式避免 view system 对显示层的直接干涉

**结果**：⏳ 尚未实测。

### 尝试 9：sublayer 模式实测 ❌ 无效

在 Mac mini M4 + 外接显示器上实测，sublayer 模式（尝试 8 的代码）**左右分裂依旧**。
排除了 `makeBackingLayer` 在 HiDPI 下被 view system 干涉的假设。

### 尝试 10：bytesPerRowAlignment 64 + IOSurface + 格式切换 flush ⏳ 待实测

三处改动：

**10a. 滤镜输出 pool 补 bytesPerRowAlignment 64 + IOSurface**

`WLBasicVideoFilter.m` — `acquirePixelBufferWidth:height:` pool 属性：

```objc
(id)kCVPixelBufferIOSurfacePropertiesKey:   @{},          // IOSurface-backed
(id)kCVPixelBufferBytesPerRowAlignmentKey:  @(64),        // Metal 纹理标准 64 字节对齐
```

**理论**：之前尝试 5 用 `@(4)` 无效，4 字节对齐太弱。Metal 纹理在 GPU 侧通常要求 64 字节对齐；若 CVPixelBuffer 的 bytesPerRow 未对齐到 64，`CVMetalTextureCacheCreateTextureFromImage` 创建的纹理 stride 可能与 buffer 不一致 → GPU 写入和 `AVSampleBufferDisplayLayer` 读取行错位 → 画面分裂。IOSurface-backed 确保 `AVSampleBufferDisplayLayer` 直接读 IOSurface 显示，无需额外拷贝。

**10b. 预览层检测像素格式切换时 flush**

`WLStreamPreview.m` — `enqueuePixelBuffer:pts:` 新增：

```objc
OSType fmt = CVPixelBufferGetPixelFormatType(pixelBuffer);
if (_lastPixelFormat != 0 && _lastPixelFormat != fmt) {
    [self flush];
}
_lastPixelFormat = fmt;
```

**理论**：滤镜关时透传 NV12，开时输出 BGRA。`AVSampleBufferDisplayLayer` 在格式切换时如果没有 flush，可能仍按旧格式的 stride/布局解析新帧 → 画面分裂。这解释了「仅颜色校正（不改尺寸）也会分裂」：虽然尺寸不变，但像素格式从 NV12 变成了 BGRA。

**10c. 合成 pool bytesPerRowAlignment 从 4 改为 64**

`WLVideoMix.m` — `ensurePool` pool 属性同步对齐，与滤镜输出 pool 一致。

**结果**：⏳ 待实测。

| 现象 | 尝试 | 结果 |
|------|------|------|

| 归零后偏色 | 2. isIdentity 阈值 | 逻辑正确，已合入 |
| 合成色彩管理 | 3. BT.709 标签 | 正确，已合入 |
| Retina 模糊 | 4. contentsScale | 改善，已合入 |
| 左右分裂 | 5. stride 对齐 | ❌ |
| 左右分裂 | 6. 去 IOSurface | ❌ |
| 左右分裂 | 7. 去 YCbCrMatrix 传染 | ❌ |
| 左右分裂 | 8. sublayer 模式（makeBackingLayer → sublayer） | ❌ 实测无效 |
| 左右分裂 | 9. sublayer 模式实测 | ❌ |
| 左右分裂 | 10. bytesPerRowAlignment 64 + IOSurface + 格式切换 flush | ⏳ 待实测 |

**结论**：
- 颜色相关 3 处修复（color attachments / isIdentity 阈值 / BT.709 标签）逻辑正确，已合入
- 左右分裂的根因不在 stride 4 字节对齐、去 IOSurface、contentsScale、YCbCrMatrix 传染、sublayer 模式
- 剩余最可能的嫌疑方向：
  1. **bytesPerRowAlignment 64 + IOSurface**（Metal 纹理标准对齐，之前仅用 4 字节太弱）
  2. **NV12 → BGRA 格式切换时 flush 显示层**（格式变化但未 flush，显示层可能按旧 stride 解析）
  3. 录制 mp4 检查是预览问题还是数据本身问题

如下格式是正常的:

### 根因分析

对比两个视频的关键差异：

| 属性 | 正常 | 不正常 |
|---|---|---|
| 编码 | H.264 Main | **HEVC Main 10** |
| 像素格式 | yuv420p (8-bit) | **yuv420p10le (10-bit)** |
| 分辨率 | 1280×720 | 3840×2160 |

**根因：10-bit HEVC 硬解时，VideoToolbox 输出的 CVPixelBuffer 格式为 `kCVPixelFormatType_420YpCbCr10BiPlanarVideoRange`，而 `WLMetalContext.bindSamplingPixelBuffer` 只识别 8-bit NV12（`420YpCbCr8BiPlanar`），10-bit 格式走到 else 分支被当作 BGRA 处理。**

10-bit YUV 的内存布局与 8-bit 完全不同（Y 平面每个 sample 16-bit），被当成 BGRA 纹理绑到 Metal 后，GPU 按 BGRA 解读 YUV10 数据，导致画面复制两份并排（10-bit 的行宽与 8-bit 不同，GPU 采样时每行只读了一半宽度）。

### 修复方案

1. **WLMetalContext.bindSamplingPixelBuffer**：新增 `kCVPixelFormatType_420YpCbCr10BiPlanarVideoRange/FullRange` 分支，用 `MTLPixelFormatR16Unorm`（Y 平面）和 `MTLPixelFormatRG16Unorm`（CbCr 平面）绑定纹理
2. **WLMetalTextureBinding**：新增 `is10Bit` 属性标记
3. **WLMetalShaderTypes.h**：`WLFilterParams` 新增 `is10Bit` 字段
4. **Metal Shader**：`fragmentShader` 和 `filterFragment` 新增 10-bit YUV→RGB 转换（R16Unorm 归一化后乘 1023 恢复 10-bit 值，再按 BT.709 video range 偏移/缩放）
5. **WLVideoMix / WLBasicVideoFilter**：传递 `is10Bit` 参数给 shader

### 复查与修正（2026-06-10，commit 5d8ecd2 之后）

复查 `5d8ecd2` 时发现两个问题，已在工作区修正（待实测后提交）：

1. **shader 10-bit video-range 亮度系数错误**：`yy = (y-64)*(1.164*255/876)` 把 Y 折算到 8-bit 数值域（乘 255/876），最后却按 1023 归一化 → 白色（Y=940）只渲染到 0.29，10-bit 源画面会暗约 3.4 倍。影响开滤镜的预览与合成/录制两条路径（`fragmentShader` / `filterFragment` 同样写法）。
2. **`WLMediaSourcePreview` 未绑 buffer(2) 隐患**：它也用 `fragmentShader`，但只绑了 buffer(0/1)；`5d8ecd2` 给 shader 新增的 `is10Bit [[buffer(2)]]` 它没绑，一旦渲染会踩未绑定 buffer。

**修正方式（简化而非改系数）**：P010 的 10 位有效值存于 16-bit 字**高位**，`R16Unorm` 采样得到的归一化值与 8-bit `R8Unorm` 一致（偏差 <0.1%），shader 根本无需区分位深。因此删除了 shader 的整个 `is10Bit` 数学分支及全链路传参（`WLFilterParams.is10Bit`、`WLMetalTextureBinding.is10Bit`、`WLVideoMix` / `WLBasicVideoFilter` 的传参、`fragmentShader` 的 buffer(2)），8/10-bit 共用原 8-bit 归一化公式。真正的 10-bit 适配只保留 `WLMetalContext.bindSamplingPixelBuffer` 的纹理格式分支（R16Unorm/RG16Unorm）——这是 `5d8ecd2` 做对的部分，也是修分裂的关键。

Debug 构建通过。**待实测**：用 Test-4K.mp4 对比「关滤镜预览 vs 开滤镜预览 vs 录制 mp4」三方亮度/颜色一致性。
