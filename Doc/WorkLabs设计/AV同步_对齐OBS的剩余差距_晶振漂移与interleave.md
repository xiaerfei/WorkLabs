## 0. 先澄清一个认知：OBS 音频不是「靠硬件时钟」

口头讨论里有个说法「OBS 音频走硬件的回调」。**一半对,但容易误导**,先校准：

- **对的那半**：音频采集确实由声卡 IO 回调（CoreAudio / WASAPI callback）驱动——声卡攒够一块 PCM 就回调一次,数据流是硬件节奏。
- **要纠正的那半**：OBS 给数据打的时间戳,**基准是系统单调时钟 `os_gettime_ns()`**（mac 底层即 `mach_absolute_time`，win 为 `QueryPerformanceCounter`），而不是声卡自己的 sample-clock。硬件回调只是「打戳的**时机**」,时钟基准用的是软件单调时钟。

**大白话**：声卡像送奶工,攒满一箱就敲门（回调）；OBS 不看奶箱上印的生产时间,而是敲门那一刻**抬头看自家墙上的钟**记下来。送奶节奏是硬件的,记的时间用的是自家那口钟。

**真正让 OBS 音频不漂移的,不是「时钟源是软是硬」,而是**：音频混音后端以 1024 样本（`AUDIO_OUTPUT_FRAMES`）为一拍**连续推进一条时间线,某源这拍没数据就用静音填窗口,时间线一格都不空**（`OBS_合成tick...md:256-291`：`audio_thread` 每 1024 采样睡到绝对时刻、每窗先清零各 mix 缓冲再叠加各源）。

> 这正是隐患 B 修法 1（混音器断流补静音）抄的作业。术语：系统单调时钟（monotonic clock）/ 混音窗口（mix window）/ 缺窗补静音（silence fill）。

## 1. WorkLabs 现状速览（两套时钟，混音器夹在中间）

| | 视频 | 音频 |
|---|---|---|
| pts 计时依据 | 墙钟读数（`(now-epoch)*1000` ms） | 累计样本数（`offset + n*1024`） |
| 代码落点 | `WLEncoder.m:300-305` | `WLEncoder.m:429-430` |
| 时间戳特性 | VFR,每帧现读真实时刻 | 由采样率恒定推算 |

两套时钟靠**共享 epoch**（同一零点）+ **音频首样本偏移**（`_audioOffsetSamples`，补迟到）+ **断流补静音**（隐患 B 修法 1）对齐。详见隐患 B 方案文档。

**关键中介——混音器 `WLAudioMixer`**：它是一个**墙钟节拍**的 `dispatch_source_timer`（每 `1024/44100 ≈ 23.22ms` 一拍,`WLAudioMixer.m:160-170`）。每拍从各路源的**环形缓冲**取最多 1024 样本混合。环形缓冲容量 `kRingSeconds = 1`（1 秒,`WLAudioMixer.m:23`）。

→ **这台「墙钟节拍 + 环形缓冲」的混音器,正是吸收声卡漂移的那道闸门**。下面差距一就围绕它。

## 2. 差距一：晶振漂移补偿（clock drift）—— 真差距,低优先

### 2.1 先讲「病」：晶振漂移是什么

声卡里有一块石英晶体（**晶振 / crystal oscillator**），通电后匀速振动,这就是声卡的「钟」——它决定声卡**每秒采集多少个样本**。

标称 `44100Hz` 的意思是「理论上每秒采 44100 个样本」。但石英晶体有制造误差,实际可能是 44100.5 或 44099.3。误差用 **ppm（parts per million，百万分之）** 衡量。

**关键：现在有两个钟在同时走**——

- **声卡的钟（晶振）**：决定音频样本「以多快速度产生」。
- **系统的钟（墙钟 / `mach_absolute_time`）**：决定「真实流逝了多少时间」。

这两个钟不完全一样快,长时间就会错开。这个错开就叫**时钟漂移（clock drift）**。例：100 ppm 偏差 = 每秒偏 0.0001 秒 = **每小时偏约 0.36 秒**。

### 2.2 一个比喻：水厂 → 水塔 → 你家用水（贯穿本节）

- **声卡** = 水厂的泵,按**水厂自己的钟**,「每秒」往你家水塔泵 44100 升水（样本）。
- **系统墙钟** = 你家墙上的标准钟。
- **混音器** = 你家,按**标准钟**每 23.22ms 从水塔放 1024 升水出去用（送编码 / 播放）。
- **水塔** = 环形缓冲（ring buffer），容量 1 秒的水（`kRingSeconds=1`）。

水厂的钟要是准,泵进来的 = 放出去的,水塔水位稳。**病就出在水厂的钟（晶振）不准。** 下面三种治法,都是在回答同一个问题：**水厂快了/慢了,这水塔怎么办?**

### 2.3 三种治法

#### 治法一：被动吸收（passive）—— WorkLabs 现在的做法

**水厂钟快了**（晶振偏快,实际每秒泵 44150 升）：进 > 出,水塔水位慢慢涨 → 涨到满（1 秒上限）→ 再来的水**进不来,溢出浪费**（丢样本）。
代码：源线程 `TPCircularBufferProduceBytes` 在缓冲满时整块写入失败 → 新样本丢弃。听感：偶尔「咯噔」跳一下。

**水厂钟慢了**（每秒只泵 44050 升）：进 < 出,水位慢慢降 → 降到空 → 要放水时没水,**只能放空气**（补静音）。
代码：`mixOnce` 里 `MIN(availBytes, wantBytes)`（`WLAudioMixer.m:206`）取不满 1024,`mix[]` 尾部保持 0。听感：偶尔「噗」一下虚。

为什么叫**被动**：混音器**从不主动测量水厂快慢、从不主动调节**,只是闷头按标准钟放水,等到水塔**满了/空了才被迫丢/补**。
- **好处**：水塔有 1 秒缓冲,平时的小抖动（线程调度 / 网络）都被水位吸收,不会动不动丢补。只有晶振漂移这种**持续性**钟速差,长期累积才会顶满/抽空。
- **代价**：丢/补的那一下是**突兀**的（跳音 / 虚音）,不平滑。而且它「盲」——不知道每杯水**正确该放在时间线的哪个位置**,只知道桶里现在有多少。

#### 治法二：主动重采样补偿（active / ASRC）—— 最平滑,最复杂

想象装了个**聪明阀门**,一直盯着水位。发现水位慢慢涨（水厂偏快）,不等满,就**把放水口稍微开大一丝**——不是丢水,而是把同样的水**「拉伸」着用**：本来 1024 升填一瓢,现在用这 1024 升填满「1025 升的瓢」。

对应音频：用**重采样（resample）**把这段样本数微微变多（或变少）,音调几乎不变（0.1% 变速人耳听不出）,水位就稳住了,**没有任何突兀的丢弃**,全程平滑。

- 术语：**异步采样率转换（ASRC, Asynchronous Sample Rate Conversion）**、**漂移补偿（drift compensation）**。FFmpeg 里是 `swr_set_compensation`（告诉重采样器「接下来帮我多塞/少塞几个样本,平滑过渡」）。
- 为什么叫**主动**：持续测量偏差、持续微调,不让漂移累积到要丢补。代价是复杂——得一直算偏差、调补偿量。
- **谁走这条路**：**mpv**（以音频为主时钟,视频去追音频对齐;见 `调研/mpv/` 系列）、专业 DAW。因为它们是单源精同步,音质瑕疵零容忍。

#### 治法三：OBS 怎么做（纠正：不是治法二）

> 口头讨论时我把治法二（ASRC）安到了 OBS 头上,**这是错的**。据调研文档 §2（音频混音）原话——「OBS 的音频混音本质是**时间对齐的浮点求和**，没有重采样到主时钟的反馈（重采样只在 audio-io 做格式/采样率适配,不做同步追赶）」（`OBS_合成tick...md:401`）——OBS **不走平滑变速那条路**,它走「给每杯水贴时间标签」的路。

1. **每杯水贴标准时间标签**：水厂每泵一批水,OBS 在**收到那一刻**按标准钟贴时间戳（`reset_audio_timing`：`timing_adjust = os_time − 源 timestamp`，`OBS_合成tick...md:444-464`）。这批水「该在时间线哪个位置」从此明确。
2. **按标签精确排队取水**：混音不是「水塔里有多少放多少」,而是「按当前这一拍的时间窗,把源数据放到 mix 缓冲的正确偏移」（`mix_audio`：`start_point = convert_time_to_frames(audio_ts − ts.start)`，`OBS_合成tick...md:368-401`）。
3. **缺口补静音**：那一拍找不到对应时间的水（断流）→ mix 缓冲每窗先清零、该源不叠加,这段就留 0,时间线照走（`OBS_合成tick...md:285,377-384`）。
4. **滞后/错位就丢或缓冲**：某源严重滞后 → `ignore_audio` 丢掉滞后采样、尝试重新对齐；慢源来晚 → `add_audio_buffering` 整条管线回退、加缓冲等它追上（`OBS_合成tick...md:326-349`）。

**所以 OBS 和 WorkLabs 是同一家族——都是「缺了补静音、滞后了丢/缓冲」,不是平滑变速。** 区别只在**判断依据**：
- **WorkLabs：只看水塔水位**（满了丢、空了补）——「盲」,不知道每杯水的正确时间位置。
- **OBS：看每杯水的时间标签**（按戳排、缺口补静音、滞后则丢/缓冲）——更「准」,知道每段数据该落时间线哪里。

### 2.4 三者归位（一张图看懂）

| 家族 | 怎么对付漂移 | 平滑度 | 谁用 |
|---|---|---|---|
| **补/丢（粗）** | 看缓冲**水位**：满了丢、空了补静音 | 有跳音/虚音瑕疵 | **WorkLabs 现状（被动吸收）** |
| **补/丢（精）** | 看**时间戳**：按戳排、缺口静音、滞后则丢/缓冲 | 仍有瑕疵,但位置精确 | **OBS** |
| **微调变速（平滑）** | **ASRC 重采样**：持续拉伸/压缩,不丢不补 | 无瑕疵 | **mpv**（音频主时钟）、专业 DAW |

> **核心洞察**：OBS 不比 WorkLabs 高级在「用了重采样」,而是高级在「用**时间戳**而不是**水位**来判断」。真正无瑕疵的平滑 ASRC 是更上面一层,只有 mpv 那种精同步播放器才需要。

### 2.5 哪些源有这个病、哪些没有

- **媒体文件源（`WLMediaSource`）**：**无此问题**。文件里写的 44100 是精确数字,没有物理晶振参与。
- **硬件采集源（`WLMicSource` 麦克风 / 将来带音频的采集设备）**：**才有**。物理晶振 → 实际速率漂移。
- **多硬件设备各自时钟不同步**（独立麦克风 + 采集卡）：漂移更突出,因为是多个晶振互相漂。

### 2.6 影响评估

| 场景 | 影响 |
|---|---|
| 录制几分钟 demo | 几乎无感（漂移量 < 几十 ms） |
| 小时级直播（硬件麦克风） | 可能可闻：周期性极轻微跳音/断续；**A/V 仍同步**（墙钟夹住） |
| 纯媒体文件录制 | **无影响**（文件采样率精确） |

> **一个反直觉但关键的好处**：因为混音器**以墙钟为准**夹住了漂移,这个漂移**不会变成「音画不同步（A/V drift）」**,而是被转化成**音频自身的微 artifact（丢样本/补静音）**。也就是说——被动吸收对「同步」反而是保护,代价只是音质上的细微瑕疵。OBS 的时间戳对齐瑕疵更小,ASRC 则连瑕疵也抹平。

### 2.7 WorkLabs 的升级路径：两档台阶,不是一步【待斟酌】

对照 2.4 的三家族,WorkLabs 要往上走是**两档台阶**（先前文档把它压成了一档「重采样补偿」,不准）：

- **第 0 档（现状 · 0 改动）**：维持被动吸收（看水位）。对录制 + 短时直播大概率够用。
- **第 1 档（对齐 OBS）**：把「看水位」升级成「看时间戳」——给混音器各路输入带上系统钟戳,按戳对齐取数、缺口补静音、超阈值重对表。**中等改动**,消除盲目丢补,延迟更可控。
- **第 2 档（对齐 mpv / 专业）**：上 ASRC 平滑补偿（`swr_set_compensation`）,瑕疵全消。**大改动**,且单源精同步才真正需要,合成直播场景收益递减。

**先决（低成本,建议先做）**：给混音器加水位 / 丢样本 / 补静音计数埋点（沿用现有 WLLog）,**先量出真实漂移量,再决定要不要从第 0 档往上爬**。没有数据之前,第 1/2 档都是过度设计。

### 2.8 待斟酌决策点

1. 目标使用场景是「短录制」还是「小时级直播」？决定漂移是否够痛、值不值得上台阶。
2. 是否先做「观测埋点」拿真实数据,再决定停在第 0 档 / 升第 1 档 / 升第 2 档？（**推荐先观测**）
3. 多硬件设备同时采集（麦克风 + 采集卡）是否在路线图内？若是,漂移更突出,第 1 档的价值上升。

## 3. 差距二：输出 interleave —— 实读后发现**基本已覆盖**（纠正先前判断）

> **修正**：隐患 B 方案文档 §3「修法 3」曾把 interleave 列为待补项。实读 `WLRecorder`/`WLPusher` 后确认：**OBS interleave 三件套,WorkLabs 已基本做齐**（第三件借 FFmpeg 实现）。此处更新认知,避免去做无用功。

### 3.1 OBS interleave 三件套 vs WorkLabs 逐件核对

| OBS 三件套（`OBS_输出侧...md:161-319`） | WorkLabs 对应 | 状态 |
|---|---|---|
| ① discard 早包（首关键帧前的包丢掉） | 等首视频关键帧才开写（Pusher `AwaitingKeyframe`）；音频 `if (outPts < 0) return` 丢首帧前音频（`WLRecorder.m:206`/`WLPusher.m:215`） | ✅ 已有 |
| ② offset 归零（首包时间戳拉到 0） | `_baseUs = 首视频包.ptsUs`；之后 `outPts = ptsUs - _baseUs`（`WLRecorder.m:155,192`/`WLPusher.m:162,201`） | ✅ 已有 |
| ③ 单调交错送出（按 dts 排序、两流交错） | **`av_interleaved_write_frame`**（`WLRecorder.m:199,214`/`WLPusher.m:208,223`）——FFmpeg 内部自带 interleave 排序队列,按 dts 缓冲、交错输出 | ✅ 借 FFmpeg 实现 |

- 流内单调性也有保障：视频 `_lastVideoPts` 强制单调（`WLEncoder.m:303`），音频样本计数天然单调；时基取 90000（视频）/ 44100（音频）够细,避免 us→tb 取整破坏 DTS 单调（`WLRecorder.m:170,177` 注释已点明）。

### 3.2 唯一残留风险：interleave 饥饿（且已被修法 1 顺带解决）

`av_interleaved_write_frame` 的排序缓冲,要「每条流都有新包」才能比较 dts 往外推。**若一条流长时间不来包**（如音频断流几秒、且修法 1 未生效不产帧）→ muxer 会**一直缓冲视频包等音频** → 延迟堆积、内存增长。

→ 而**隐患 B 修法 1（断流补静音）恰好顺带解决它**：音频持续产帧 → 两条流都有包 → interleave 正常推进。所以这个残留风险**和修法 1 是同一把钥匙**。

### 3.3 结论【待斟酌】

- **不建议**把 interleave 当独立大改项做——三件套等价物已具备。
- 若将来真要「加固」,顶多是**观测**（interleave 队列深度埋点）或在 stop 时确认 flush 完整（`av_write_trailer` 已会排空队列,`WLRecorder.m:100`/`WLPusher.m:92`）。优先级：**低**。

## 4. 汇总：两块差距的取舍

| 差距 | 是否真差距 | 影响面 | 优先级 | 建议下一步 |
|---|---|---|---|---|
| 晶振漂移补偿 | ✅ 真差距 | 仅硬件采集源 + 小时级时长；A/V 仍同步,瑕疵在音质 | 中低 | 先做「观测埋点」量真实漂移；再决定停第 0 档 / 升第 1 档（对齐 OBS·时间戳）/ 升第 2 档（对齐 mpv·ASRC） |
| 输出 interleave | ⚠️ 基本非差距（已覆盖） | 残留「饥饿」已被修法 1 解决 | 低 | 不单独做；顶多加队列深度观测 |

**先决条件**：这两块都建立在**隐患 B 修法 1 已实测验证**的前提上（断流补静音是漂移吸收 + interleave 不饥饿的共同地基）。建议**先把修法 1 实测过**（设置→测试页→模拟断流 3 秒,ffprobe 比 audio/video duration）,再回头斟酌这两块。
