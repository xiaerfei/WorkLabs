## 1. 问题：音频会在断流后「超前」于视频

### 1.1 现象（预测，待实测）

持续出声时不漂；一旦音频中途**断供**（媒体文件 seek / 暂停、麦克风掉数据、设备静音），断流恢复后**音频比视频提前**，而且**每断一次累积一点**。术语：**A/V drift（音视频漂移）**。

### 1.2 大白话：两个钟走法不一样

- **视频的钟 = 挂墙上的钟**。`WLEncoder` 给视频帧打的 pts 直接取墙钟（`WLEncoder.m:300-305`，`(now - epoch) * 1000` 毫秒）。断流？墙钟照走，pts 照跳。术语：**系统时钟域 / wall-clock**。
- **音频的钟 = 数米粒的钟**。`WLEncoder` 给音频帧打的 pts 是「收到多少样本就走多少格」（`WLEncoder.m:429-430`，`pts = _audioOffsetSamples + _aNextPts`，每编出一帧 `_aNextPts += 1024`）。术语：**样本计数域 / sample-count**。
- 平时两个钟一样快：1 秒 = 44100 粒米 = 墙钟 1 秒，对得上。
- **但音频这碗米是「混音器」按节拍一勺勺递的**，而混音器在**所有音频源这一拍都没数据时，干脆不递这一勺**（`WLAudioMixer.m:203` `if (!any) return;`）。
- 断流那几秒：墙钟照走，音频的「数米钟」**停摆**。断流恢复，音频接着上次的格子继续数 → **断流那段的「时长空白」被音频吞掉了** → 音频整体提前。

### 1.3 精确根因（代码级链路）

```
音频源断流（无数据写入环形缓冲）
   │
   ▼  WLAudioMixer.mixOnce()  每 23.22ms 一拍
   if (!any) return;                       ← WLAudioMixer.m:203【根因】这一拍不产帧
   │
   ▼  （没有混音帧产出 → audioBufferOutput 不触发）
   WLEncoder 的音频 FIFO 不增长
   │
   ▼  drainAudioFifo 没有满 1024 可编 → 不出帧
   _aNextPts 不推进                          ← WLEncoder.m:430
   │
   ▼  音频 pts 停在断流前的值；恢复后接着 +1024
   音频时间轴「丢失了断流时长」→ 比视频墙钟短 → 音频超前
```

视频侧对照：`encodePixelBuffer` 每帧都按墙钟打 pts（`WLEncoder.m:300-305`），断流也照推，**所以视频不丢时长**。

> **一句话**：**范式混杂**——视频锚系统时钟、音频靠样本计数；而「样本计数 ≡ 墙钟时长」依赖一个隐含前提「混音器每拍都产帧」，`if(!any) return` 在断流时打破了这个前提。

## 2. OBS 怎么避免的

| OBS 机制 | 做法 | 出处 |
|---|---|---|
| 音频也锚系统时钟 | `audio_time = start_time + 样本数→纳秒`，音频线程 `os_sleepto_ns_fast` 睡到**绝对刻度** | `OBS_合成tick...md:256-283` |
| **混音窗口每拍都处理** | 源没数据就**贡献 0（静音）**，**时间轴永不中断** | `OBS_合成tick...md:337-402` |
| 源入口归一 | `timing_adjust = os_time − 源PTS`，各源帧统一到同一墙钟轴 | `OBS_合成tick...md:444-464` |
| 输出层 interleave 三件套 | discard 早包 → offset 归零 → 单调交错送出 | `OBS_输出侧...md:161-319` |

**关键洞察**：OBS 音频不漂，**不是「用系统时钟打戳」这个动作本身**起的作用，而是**混音器按墙钟节拍持续产帧（静音也产）**，使得「累计样本数 ≡ 墙钟流逝时长」恒成立。

**而 WorkLabs 的混音器本来就已经是墙钟节拍的 `dispatch_source_timer`**（每 `1024/44100 ≈ 23.22ms` 一拍，`WLAudioMixer.m:151-157`；dispatch timer 按绝对时间表调度，间隔不累积漂移）——**唯一缺的就是「没数据时也产静音帧」这一步**。

## 3. 修法选项

### ✅ 修法 1（推荐）：混音器断流时补静音帧

把 `WLAudioMixer.mixOnce` 改成：**一旦开始过（收到过真实数据），即使本拍无数据，也输出一帧全 0 的 1024 样本**。

- **效果**：混音器严格按墙钟节拍持续产帧 → `WLEncoder` 收到的样本数 ≡ 墙钟流逝 → `_aNextPts` 自动跟上墙钟 → 音频不漂。**`WLEncoder` 一行都不用改**（它现有的样本计数自动变得与墙钟一致）。
- **改动面**：仅 `WLAudioMixer`（加一个「已激活」标志 + 无数据时产静音帧）。
- **大白话**：让「数米钟」在断流时**自动往碗里补米（静音）**，米粒数就永远等于流逝的时间。
- **两个注意点**：
  1. 用「已激活（至少一路写过真实数据）」标志，避免「完全没有音频源时混音器空转狂产静音」——纯摄像头场景下 `audioEnabled=NO` 本来就会丢弃这些帧，但省得无谓空转 + 占 CPU。
  2. 摄像头那路 input 是恒空的（视频源也被 `addInput`，见 `WLStreamsManager.m:120`，但它从不写音频）。靠「已激活」区分「真有音频源但暂时断流（→补静音）」与「压根没有音频源（→不产）」。

**伪代码**（对照 `WLAudioMixer.m:180-216`）：

```objc
- (void)mixOnce {
    float mix[1024*2] = {0};
    BOOL any = NO;
    @synchronized (self) {
        if (!self.running) return;
        for (各路 input in self.inputs) {
            从环形缓冲取 MIN(avail, 1024) 样本, 增益后累加进 mix[];
            if (取到了数据) any = YES;
        }
    }

    if (!any) {
        if (!self.everProduced) return;   // 还没开始过 → 不产（纯视频场景不空转）
        // 已激活但本拍断流：产一帧静音补齐墙钟时间轴（mix[] 已是全 0）
    } else {
        self.everProduced = YES;
    }

    限幅 mix[] 到 [-1, 1];
    CMSampleBufferRef sb = [self makeSampleBufferFromFloats:mix samples:1024];
    self.mixedOutput(sb);   // 静音帧同样走播放 + 录制；录制侧靠它补齐音频时长
}
```

> 唯一改动相对 `:203`：把无条件 `if(!any) return` 换成「`everProduced` 之后即使 `!any` 也产静音帧」。

### 修法 2：在 `WLEncoder` 音频侧按墙钟重戳（更彻底，但改动大）

不依赖混音器，在 `WLEncoder` 音频侧每帧用 `(now - epoch) * 44100` 算「应有样本位置」，落后则补静音、对齐 pts。这是 OBS 的完整范式，但 **WorkLabs 的混音器已经是墙钟节拍**，修法 1 已等效达成同样效果。修法 2 等于重复造轮子且更复杂——除非将来去掉混音器定时器，否则不必。

### 修法 3：输出层 interleave 加固（另一维度，不是本隐患）

OBS 输出层三件套（discard 早包 → 归零 → **按 dts 单调交错送出**，`OBS_输出侧...md:161-319`）。WorkLabs 的 `WLRecorder` 现在是「每包实时写」。这解决的是**「muxer 收到非单调 dts 会报错/丢帧」的健壮性**问题，**不是 drift**。建议作为**后续独立项**，与隐患 B 解耦。

## 4. 推荐 + 验证

**推荐修法 1**：精确命中根因（`WLAudioMixer.m:203` 跳帧）、改动最小、契合 OBS「混音窗口始终处理、缺数据贡献 0」范式、`WLEncoder` 零改动。

**实测验证（修法落地后）**：
1. **构造断流**：①播放媒体文件录制，中途 seek / 暂停几秒再继续；②或麦克风录制中途把设备静音/拔掉几秒再恢复。
2. **量 drift**：断流前后各拍一次手做参照点；录完用 `ffprobe` 比 `audio duration` vs `video duration`（修法前音频会明显偏短；修法后应接近，差 < 0.2s）。
3. **对照**：修法前——断流后音画错位（音频提前）；修法后——始终对齐。

> 注意：修法 1 只解决 **drift（时间轴长度）**。多路音频的**对齐/音质**（各路供给不均时静音穿插）是另一个独立的混音质量问题，不在本方案范围。
