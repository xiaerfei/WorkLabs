## 零、一句话结论

这条链路有**两套采集实现**（AudioUnit RemoteIO / AudioQueue），选哪套完全由
`TVURecorder.realization` 决定，而该属性只在 `TVUAudioCaptureManager` 里被赋值。
两套回调的内部处理顺序**逐行同构**，最后都汇聚到
`-[TVURecorder sendToEncoderWithAudioData:...]` 做统一分包，再由
`aacEncoder::sendFrameToEncoder()` 做四路分叉。

**`aacEncoder` 里的 `PCMFrame` / `PCMFrameList` / `doencode()` / `tvu_mic_pcm_separator`
线程在这个 checkout 里是死代码**（见 §六），mic 的实际出口只有
`sendFrameToEncoder()` 一个函数。

```objc
if (self.isHaveChangedInput) { return; }                      // :1321  完全不动

if ([self isPlugUSB] || [self isPlugStereoMicrophoneWired]) {  // :1329
    self.realization = AudioRealizationAudioQueue;             // :1331
} else if([self isExistUSBMic]) {                             // :1332
    self.realization = AudioRealizationAudioQueue;             // :1334

```

即：**USB 音频 / 有线立体声麦克风 / 系统里存在 USB mic ⇒ 强制 AudioQueue**，
其余情况才听参数 `isOn`。

`isExistUSBMic`（`:1412`）的注释给了原因（`:1406-1411`）：

> 是否存在usb mic , 如果存在usb 设备，蓝牙和usb都以 audio queue 采集，因为使用audio unit采集，设备会丢失。
> 原因：回声消除模式导致，具体原因未知

三个判定的实现：
- `-isPlugUSB` `:1379` — 遍历 `currentRoute.inputs`，匹配 `AVAudioSessionPortUSBAudio`
- `-isPlugStereoMicrophoneWired` `:1402` — 转发 `+[TVUAudioInputSourceTool isWithStereoMicrophoneWired]`
- `-isExistUSBMic` `:1412` — `+[TVUAudioInputSourceTool isHaveSystemSwitchAudioSoureWithType:TVUAnywhereAudioCaptureType_USBMIC]`

### 1.3 AudioUnit 的三种 componentSubType

`-initAudioComponent`（`TVURecorder.mm:1884-1924`）按编译宏 + 设置项选 subType：

| 编译条件 | `_isVoiceProcessingUnit` | `componentSubType` | 行号 |
|---|---|---|---|

### 2.1 步骤 6：增益施加点

增益是**回调里第一个真正改 PCM 内容的操作**，在所有旁路（WebRTC/VoIP/屏共/编码器）
之前，所以**所有下游都吃到同一份加过增益的数据**。

```objc
// TVURecorder.mm:525-541（AudioUnit）
if (recorder.gain != 1.0) {
    static UInt32 gain_size = 0;
    static uint8_t *gain_data = NULL;
    if (gain_size == 0) {
        gain_size = bufferSize * 2;
        gain_data = (uint8_t *)malloc(gain_size);
    } else if (gain_size != bufferSize) {
        gain_size = bufferSize * 2;
        gain_data = (uint8_t *)realloc(gain_data, gain_size);
    }
    memset(gain_data, 0, gain_size);
    if (gain_data != NULL) {
        [recorder setCaptureGainWithSource:(uint8_t *)bufferData andSourceSize:bufferSize andOutSource:gain_data];
        memset(bufferData, 0, bufferSize);
        memcpy(bufferData, gain_data, bufferSize);
    }
}
```

要点：
- `gain == 1.0` 时整段跳过，零拷贝。
- 中转 buffer 是 `static`（跨回调复用），容量按 `bufferSize * 2` 分配。
- 判定条件写的是 `gain_size != bufferSize`，而分配的是 `bufferSize * 2`，所以
  **只要块大小稳定，第二次回调起每次都会 `realloc`**（`gain_size == 2*bufferSize != bufferSize`）。
  功能上无害（`realloc` 到同样大小），但是在实时线程上每帧一次 `realloc`。
  AudioQueue 版同样问题（`:769`）。
- 结果**原地回写**进 `bufferData` / `inBuffer->mAudioData`。

`-setCaptureGainWithSource:andSourceSize:andOutSource:`（`TVURecorder.mm:2632-2663`）：

```objc
int const MAX = 32767;
int const MIN = -32768;
double f = 1;
for (int i = 0; i < bufferSize/2; i ++) {
    double temp = ((*(short *)(bufferData + (i << 1))) * self.gain);
    double output = (temp * f);
    if (output > MAX) { f = (double)MAX / (double)(output); output = MAX; }
    if (output < MIN) { f = (double)MIN / (double)(output); output = MIN; }
    if (f < 1) { f += ((double)1 - f) / (double)32; }
    *(short *)(outData + (i << 1)) = (short)output;
}
```

即**逐 int16 采样点乘 gain，带一个软限幅器**：削顶时把衰减因子 `f` 压下去，
之后每个采样点让 `f` 以 1/32 的步长回爬到 1（一个简单的 release 曲线）。
`f` 是**局部变量**，每次调用（每个块）从 1 重新开始，不跨块保持状态。
按 int16 遍历，不区分声道 —— 双声道时左右道用同一个 `f`。

### 2.2 步骤 5：静默音检测其实是死闸门

`isSilenceCarAudioBuff()`（`TVURecorder.mm:184-266`）返回值**永远是 NO**：

- `:185` `if (!openDebugViewOnSetting) return NO;` —— `openDebugViewOnSetting` 在
  `-startRecorder`（`:1284`）由 `TVUSettingStorage.storage.enableDebugView` 赋值。
- 真正想返回 YES 的那段（`:234-263`，`silence_cnt >= 15` 即 1.5s 全静默后重启音频）
  **`return YES;` 被注释掉了（`:262`）**，只剩
  `[[TVUAudioCaptureManager manager] sureDeviceIsSilence:...]` 上报（`:235`）。
- 函数唯一出口是 `:265 return NO;`。

所以它当前**只有埋点/日志作用**（`updateAudioSilenceLog:time:type:`），不会丢帧。

> ⚠️ 潜在隐患：如果哪天恢复 `return YES`，**AudioQueue 侧 `:760` 的 `return` 没有先
> `AudioQueueEnqueueBuffer`**，会漏掉一个队列 buffer（三个 buffer 漏完就彻底停采）。
> AudioUnit 侧无此问题。

### 2.3 步骤 11/12：静音是 memset，不是丢帧

三个静音源，都是把 PCM 抹零后**继续往下送**（保 PTS 连续）：

| 条件 | AudioUnit | AudioQueue |
|---|---|---|
| `[[TVUIntegrateAgoraTools getInstance] getIsCloseAudioOnAgora]` | `:593-595` | `:808-810` |
| `[recorder appVoiceState] == TVUAnywhereVoiceState_Slience` | `:598-600` | `:813-815` |
| `isAccsoonWithBuildIn`（Accsoon 无音频流时借内置 mic 保时基） | `:598-600` | 无 |

`TVUAnywhereVoiceState_Slience` 来自 SDK 公开接口
`-[TVUAnywhere tvuSetVoiceState:]`（`TVUAnywhereSDK/TVUAnywhere.mm:2148`）→
`-[TVUAudioCaptureManager setVoiceState:]`（`TVUAudioCaptureManager.mm:159`）。
枚举定义 `TVUAnywhereSDK/TVUAnywhere.h:31-32`。

Accsoon 的注释在 `:564-569`：

> 是否在连接Accsoon的时候使用内置mic的声音。
> 当检测Accsoon 设备没有音频流时候，使用内置mic的音频流，并且把音频流设置成静音

注意 §9 的 `+isSendAuidoToEncoder` 闸门在 AudioUnit 侧带 `&& !isAccsoonWithBuildIn`
（`:580`），也就是 **Accsoon 借时基这条路会绕过总闸门**；AudioQueue 侧没有这个例外（`:800`）。

### 2.4 步骤 7：WebRTC / VoIP 上行旁路（不在主链上）

这两路是**旁路**，不影响后续送编码器，但它们在实时线程上执行且会加锁：

- `-pushWebRTCAudioData:dataSize:timestamp:`（`TVURecorder.mm:2357-2402`）
  - `:2360` 第一道闸门 `![[TVUWebRTCManager shareInstance] voipIsCalling]` → return
  - `:2369` 若 `mRecordeAudioSamplerate != self.webRTCSampleRateSDP`，分包成 1024 采样点
    （`needPcmSize = 1024 * channel * 2`，`:2377`）后交
    `-resampleToWebRTCAudioData:andSize:andNowTime:`（`:2507`）
  - `:2390-2396` 否则若双声道，**取左声道降单声道**（`monoAudioData[i] = data[2*i]`）
    再 `tvuWriteAudiodataToWebRTC:`
  - 注意这里传的时间戳是 `nowTime`（当前 host 时钟秒），**不是** `currentTime`
- `TVURTILVoIPManager pushAudioData:...`（AudioUnit `:555`，AudioQueue `:783`），
  仅 `TVUOnlyAnyWhere` 编译

`-resampleToWebRTCAudioData:`（`:2507-2578`）内部：`self.resampleWebRTCLock` 加锁 →
按 (`sampleRate`,`srcSampleRate`,`srcChannel`) 三元组变化重建 `TVUFFmpegResample`
（`:2532-2547`）→ `convertor_feed_data:` → `subcontractWithInBuffer:...` 再分包成
`mBytesPerFrame = (16/8)*1 = 2` 的 2048 块回调出去。

## 三、采样率 / 声道适配

### 3.1 硬件采样率从哪来

`TVURecordConfig`（`TVURecordConfig.mm`）是唯一的采样率决策点：

```objc
- (int)getAudioRecordSampleIsBluetooth:(BOOL)isBluetooth {   // :36
    if (isBluetooth) return [self getCurrentBluetoothSampleRate];
    return kTVUDefaultSampleRate;                            // 48000
}
```

- `kTVUDefaultSampleRate = 48000`、`kTVUBluetoothSampleRate = 16000`（`TVURecordConfig.h:10-11`）
- 蓝牙采样率是**持久化的用户设置**：`NSUserDefaults` key `kTVUBlueToothSampleRate`
  （`TVURecordConfig.mm:30-31, 45`），默认值也是 48000
- 也就是说：**只有"蓝牙 + 用户把蓝牙采样率设成 16k"这一种情况才会 != 48k**
  （`TVURecorder.mm:830-834` 的注释确认：「目前只有在tvuanwhere 里面采集的声音可能是 16k。
  在其他项目默认都是48k」）

启动 AudioUnit 时还会主动请求 48k 硬件采样率与 IO buffer 时长：

```objc
[[AVAudioSession sharedInstance] setPreferredSampleRate:kTVURemoteSampleRate error:&error];      // :1618
[[AVAudioSession sharedInstance] setPreferredIOBufferDuration:kTVUAudioIOBufferDuration error:&error];  // :1626
```
`kTVURemoteSampleRate = 48000.0`（`:103`），
`kTVUAudioIOBufferDuration = 1024.0/48000.0 ≈ 21.33ms`（`:104-105`）。
启动成功后还会**再设一次** `setPreferredIOBufferDuration`（`:1660`），
注释（`:1650-1657`）说是为了修 iPhone 15 + CarPlay 下 buffer size 变 8192 的问题。

### 3.2 非 48k 时的重采样路径

`-sendNeedResampleAudioData:dataSize:timestamp:`（`TVURecorder.mm:2236-2298`，
`_TVUSDKPartyline` / `_TVUSDKANYWHERELITE` 下整段不编译）：

```objc

    if (resampleOutDataSize < covertSize) resampleOutDataSize = covertSize + 512;
    resampleOutData = (uint8_t *)malloc(resampleOutDataSize);
}
[self.resampleLock unlock];

static NSMutableData * pcmCacheResampleData = ...;                        // :2262
...
[pcmCacheResampleData appendBytes:mAudioData length:mAudioDataByteSize];  // :2271
uint64_t correct_pts = timestamp - remain_pts;                            // :2273

    uint8_t *data = (uint8_t *)pcmCacheResampleData.bytes;

```

重采样参数由 `-getResampleDicWithInputSampleRate:outPutSampleRate:`
（`TVURecorder.mm:2070-2089`）拼出：

| key | 值 |
|---|---|

- `*outSize`（`:271`）是 **字节数**，来自
  `av_samples_get_buffer_size(&dst_linesize, dst_nb_channels, tmp_ret, dst_sample_fmt, 1)`（`:261-262`）。
- `memcpy(outBuffer, dst_buffers[0], converted_size)`（`:272`）—— **outBuffer 由调用方持有并负责容量**，
  接口里没有容量参数也没有边界检查。
- 任何早退分支（`:213/216/245/250/259/269`）都**不写** `*outSize`，所以调用方必须自己预置 0
  （`TVURecorder.mm:2276` 的 `int outSize = 0;` 就是为此）。
- 类内**没有任何锁**，也没有 `dealloc`。线程安全完全由调用方负责 —— 这就是
  `TVURecorder` 用 `self.resampleLock` 包住每一次使用的原因。
- 仓库内**所有**调用方的 `andSrcNBSample:` 都传 `1024`。

> ⚠️ **可疑点（未确认是否为现网 bug）**：`TVURecorder.mm:2279` 喂进去的
> `andLen:` 写死为 `kTVURecoderPCMMaxBuffSize`（2048），而 `:2293` 从缓存里丢弃的是
> `needPcmSize = 2048 * mRecordeAudioChannel`。
> 当 `mRecordeAudioChannel == 2` 时：
> 1. `src_buffers[0]` 的 linesize 是 `1024 帧 × 2 声道 × 2 字节 = 4096`，`memcpy` 只填了 2048，
>    **后一半是上一轮的残留**；
> 2. `swr_convert` 仍按 `_src_nb_samples = 1024` 帧转（`:253`），所以那半截残留会被当成有效数据；
> 3. 调用方却从缓存丢弃 4096 字节，**真实数据的后一半直接丢掉**。
>
> 实践上触发不到：非 48k 只发生在蓝牙，而 `-getCurrentAuidoChannel`（`:2704`）
> 只在"有线立体声麦克风 / USB mic"两种情况返回 2，蓝牙走的是 1 声道。
> 单声道时 `1024 帧 × 1 × 2 = 2048` 正好对齐，无问题。**需运行时验证能否构造出该组合。**

## 六、PCM 分包

### 6.1 两级分包

```
硬件块（inNumberFrames 可变）
  → -sendToEncoderWithAudioData:...   （NSMutableData 攒够 needPcmSize 就切一块）
      → aacEncoder::sendFrameToEncoder()   （不再分包，直接分叉）
```

`-sendToEncoderWithAudioData:samplerate:channels:dataSize:timestamp:`
（`TVURecorder.mm:2309-2352`）是**唯一的分包器**：

```objc
int needPcmSize = kTVURecoderPCMMaxBuffSize * mRecordeAudioChannel;   // :2323  2048 * ch
NSInteger remainDtaSize          = self.pcmCacheData.length;
NSInteger samplesPerChannel      = remainDtaSize / (channel * sizeof(int16_t));
NSInteger needSamplesPerChannel  = needPcmSize   / (channel * sizeof(int16_t));   // 恒为 1024
uint64_t remain_pts   = samplesPerChannel     * 1000 / samplerate;
uint64_t need_pcm_pts = needSamplesPerChannel * 1000 / samplerate;                // 1024*1000/48000 = 21
[self.pcmCacheData appendBytes:mAudioData length:mAudioDataByteSize];
uint64_t correct_pts = timestamp - remain_pts;
while (self.pcmCacheData.length >= needPcmSize) {
    uint8_t *data = (uint8_t *)self.pcmCacheData.bytes;
    aacEncoder::get_instance()->sendFrameToEncoder((uint8_t*)data, needPcmSize, correct_pts, mRecordeAudioChannel);
    [self.pcmCacheData replaceBytesInRange:NSMakeRange(0, needPcmSize) withBytes:NULL length:0];
    correct_pts += need_pcm_pts;
}
```

缓存是**实例属性** `self.pcmCacheData`（`TVURecorder.mm:975` 声明，`:1257` 初始化，
`TVURecorder.h:130` 暴露为 readonly），不是 static —— 与重采样路径里那个
`static NSMutableData * pcmCacheResampleData`（`:2262`）是两个独立缓存。

### 6.2 块规格表

| 位置 | 字节 | 声道 | 采样率 | 每声道采样点 | 时长 |
|---|---|---|---|---|---|
| AudioQueue 分配的 buffer | `2048 * mRecordeAudioChannel`（`:1509`） | 1 或 2 | 硬件率 | 1024 | 21.33ms @48k |
| AudioUnit 每次回调 | `inNumberFrames * 2 * mRecordeAudioChannel`（`:447`） | 1 或 2 | 硬件率 | `inNumberFrames`（期望 1024，不保证） | ~21.33ms |

| 分包器输出 `needPcmSize` | `2048 * channel` | 1 或 2 | 48000 | **1024**（两种声道都是 1024） | **21.33ms** |
| 转双声道后 | `4096` | 2 | 48000 | 1024 | 21.33ms |

## 八、PTS 来源

### 8.1 计算式

两套回调完全一致（AudioUnit `:392-407`，AudioQueue `:717-731`）：

```objc
CMClockRef hostClockRef = CMClockGetHostTimeClock();
CMTime hostTime = CMClockGetTime(hostClockRef);
Float64 nowTime = CMTimeGetSeconds(hostTime);                                     // 墙上时钟(秒)

Float64 now_audio_pts = CMTimeGetSeconds(
    CMClockMakeHostTimeFromSystemUnits(inTimeStamp->mHostTime));                  // 采样时刻(秒)

static Float64 audio_base_time = nowTime;        // 函数级 static，首次回调初始化
static Float64 first_audio_pts = now_audio_pts;

if (isResetAudioBaseTime) {
    isResetAudioBaseTime = false;
    first_audio_pts = now_audio_pts;
    audio_base_time = nowTime;
}
Float64 currentTime = audio_base_time + (now_audio_pts - first_audio_pts);        // 秒
```

然后：

```objc
Float64 current_frame_pts = currentTime * 1000;                                   // 毫秒  (:604 / :826)
```

分包器里再校正（`:2329-2334`、`:2350`）：

```objc
remain_pts   = (cachedBytes / (channel * 2)) * 1000 / samplerate;      // 已缓存数据的毫秒数
need_pcm_pts = 1024 * 1000 / samplerate;                              // 48k → 21 (整数除!)
correct_pts  = current_frame_pts - remain_pts;                        // 第一块的 PTS
// 每输出一块： correct_pts += need_pcm_pts
```

最后（`aacEncoder.mm:285`）：

```objc
encodeParam.pts = (Float64)(timestamp / 1000.0);        // 毫秒 → 秒（Float64）
```

下游（越界，供对照）`TVUAudioEncoderManager.mm:145`：
```objc
int64_t newPts = (int64_t)((param->pts - g_vstarttime) * 1000);   // 相对视频起点的毫秒
```

### 8.2 关键事实

- **PTS 的原始来源是 `AudioTimeStamp->mHostTime`**（AudioUnit 侧 `inTimeStamp->mHostTime`，
  AudioQueue 侧 `inStartTime->mHostTime`），经
  `CMClockMakeHostTimeFromSystemUnits` 换成 CMTime 再取秒。
- `g_tvustartcaptureTime` **不参与** mic PTS 的计算。它是 `int64_t` 微秒，
  定义在 `TVUAnywhereSDK/TVUPSClient/CameraWriterVideoManager.mm:28`，
  由**视频编码器**首帧赋值（`TVUVideoH264Encoder.mm:393` / `TVUVideoH265Encoder.mm:456`），
  只在封装层（`AVFormatHttp.mm:139` 等）用。
- `g_vstarttime`（`TVURecorder.mm:89` 定义为 `Float64`，秒）同样由**视频编码器**首帧赋值
  （`TVUVideoH264Encoder.mm:390` / `H265:453` / `TVUAVStreamManager.mm:2815`）。
  在 mic 链上它只出现在 `filterInvalidAudioSample` 的**日志**里（`:884`、`:895`）。
- `audio_base_time` / `first_audio_pts` 是**函数级 static**，两套回调各有一份，
  互不共享。设备切换/AudioUnit↔AudioQueue 切换时靠全局
  `isResetAudioBaseTime`（`:131`）重锚。
- `isResetAudioBaseTime` 的写入点：`:131` 初值 `true`、`-startRecorder` `:1292`、
  `filterInvalidAudioSample` 的两个跳变分支（`:902`、`:915`）。
  注释（`:123-130`）：ITA-905 rod device in partyline。
- **`need_pcm_pts` 是整数除法**：`1024*1000/48000 = 21`（真值 21.333ms）。
  单个回调内多输出一块就少 0.33ms。但每次回调的 `correct_pts` 都用新的
  `current_frame_pts` 重锚，所以误差不跨回调累积。
  16k 时 `1024*1000/16000 = 64`，恰好整除。
- 单位链：`mHostTime`(host ticks) → 秒(Float64) → **毫秒(Float64 → uint64_t)** → 秒(Float64)。
  `-sendToEncoderWithAudioData:...:timestamp:(uint64_t)` 的形参是 `uint64_t`，
  实参是 `Float64 current_frame_pts`，**这里有一次隐式截断到整毫秒**。

`static` 在文件作用域 = 内部链接，**每个 include 它的 .mm 各得一份拷贝**；
`static inline` 函数里的 `static dispatch_once_t onceToken` 同理。
所以每个 TU 都会 `dispatch_queue_create` 一个**同名但不同实例**的
`com.tvu.audio.capture` 串行队列。

直接 include `TVURecorder.h` 的 TU 只有两个（已全仓库确认）：
- `TVUAnywhereSDK/TVUAudioCapture/TVURecorder.mm`
- `TVUAnywhereSDK/TVUAudioCapture/TVUAudioCaptureManager.mm`

include `MainViewController.h` 的 TU。）

1. **`TVUAudioCaptureManager.mm` 里的 `audioRouteChanged:` 与 `TVURecorder.mm` 里的

`TVURecorder.h:18-27` 的注释描述的是"一个串行队列控制音频采集的创建与销毁"，
按当前链接语义**并没有做到**。这是静态推断（C/C++ 内部链接语义），未在运行时用
`dispatch_queue_get_label` + 指针比对验证。

## 十二、不确定 / 需运行时验证的点

1. **AudioQueue 回调线程名未确认。** `AudioQueueNewInput` 的 `inCallbackRunLoop` 传了
   `NULL`（`TVURecorder.mm:1488`），按文档是系统内部线程，但具体线程名（以及是否
   real-time 优先级）需要真机 `pthread_getname_np` / Instruments 确认。
   AudioUnit 侧同理（通常叫 `AURemoteIO::IOThread`，未在本仓库验证）。

2. **`inNumberFrames` 的真实取值未确认。** 代码假设 1024（`setPreferredIOBufferDuration`
   = 1024/48000），但注释（`:441-446`、`:494-510`）明确说过它会动态变化
   （举例 1920/2880/8192）。分包器能吸收变化，但 G2 闸门（`> 10240` 字节）在双声道 +
   大 buffer 时是否会误伤，需实测。

3. **§3.2 的 `convertor_feed_data:andLen:` 传 2048 而丢弃 `2048*channel`** ——
   双声道 + 非 48k 是否真的能同时出现（进而丢一半数据），需要构造场景验证。
   静态分析看不到这个组合的入口。

4. **增益 buffer 每帧 `realloc`**（§2.1）：`gain_size != bufferSize` 的判定与
   `gain_size = bufferSize*2` 的赋值不自洽。是否真的每帧调用 `realloc`（以及开销），
   建议真机 profile 确认。

5. **`isSilenceCarAudioBuff` 恒返回 NO** 的结论基于 `:262` 的 `return YES` 被注释。
   如果日后恢复，AudioQueue 侧 `:760` 缺 `AudioQueueEnqueueBuffer` 会漏 buffer ——
   这是静态推断，未实测。

6. **`filtratePTS()` 无调用方** 的结论来自全仓库 grep（只命中 `:133` 声明与 `:929` 定义）。
   若有 C 链接的外部调用（如别的 target 里 `extern`），本次未覆盖。

7. **`__state` 恒为 `AAC_ENCODE_STATE_SET`** 的结论基于 `startEncode`/`endEncode` 函数体
   全被注释。已 grep 确认 `aacEncoder::doencode()` 无其它调用方，但没有运行时日志佐证
   （若跑一遍应该看到 `"aac encoder is not ready, drop it"` 从不出现，因为
   `pushFrame`/`pushOnechannelFrame` 的调用点也全是注释）。

8. **`resampleOutData` 容量是否够用未验证。** §3.2 里按
   `max(needPcmSize*5, 48000/srcRate*needPcmSize + 512)` 分配，而
   `TVUFFmpegResample` 的实际输出上限含 `swr_get_delay` 残留（`TVUFFmpegResample.mm:230-231`），
   且 `-convertor_feed_data:...` 的 `memcpy`（`:272`）**没有边界检查**。
   16k→48k、1024 采样点的情况下 3 倍 + delay 应该远小于 5 倍余量，但没实测。

9. **`TVUFFmpegResample` 的三处线程/边界隐患**（均为静态观察，未复现）：
   - `.mm:299` `static int packetSize = needPacketSize;` 是**函数级 static，跨实例跨线程共享**，
     由最先到达的调用方一次性初始化 —— 与 `.mm:55-61` 那条「不要使用static 变量，防止多线程不安全」
     的 ITA-905 注释自相矛盾。
   - `.mm:307` `memcpy(pcm_buffer + pcm_buffer_size, in_buffer, in_zize)` 写进固定 20480 字节的
     成员数组（`pcm_buffer[kTVURecoderPCMMaxBuffSize*2*5]`），无容量检查。
   - `.mm:334` `memset(pcm_buffer_temp, 0, pcm_buffer_size)` 用 `pcm_buffer` 的长度去清
     `pcm_buffer_temp`（后者只有 `packetSize` 大，且首次 `subcontractWithInBuffer:` 之前是 NULL）。
     `-resetSubContractBuffer` 紧跟 init 调用时之所以安全，只因为那时 `pcm_buffer_size == 0`。
   - 类里**没有 `dealloc`**，`pcm_buffer_temp`（`.mm:301` malloc）会泄漏。
   这些主要影响 WebRTC 旁路（`-resampleToWebRTCAudioData:` 用了 `subcontract`），
   mic 主链只用 `convertor_feed_data:`，不碰 `subcontract`。

10. **§9.3 的"每 TU 一个队列"是静态链接推断**，未在运行时用
    `dispatch_queue_get_label` + 队列指针比对确认。若编译器/链接器做了 identical-code-folding
    之类的合并（正常不会合并 `static` 变量），结论会不同。

11. **`setPreferredInputNumberOfChannels:1`（`TVUAudioCaptureManager.mm:305`）与
    `-getCurrentAuidoChannel` 在 USB 时返回 2（`TVURecorder.mm:2709-2712`）的矛盾**：
