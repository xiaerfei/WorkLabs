## 零、先纠三处常见误解

写在最前面，因为它们会直接影响读代码的方向。

### 0.1 `RPSampleBufferTypeAudioMic` 已经被注掉了 —— 屏录链路的 "Mic 音频" 不来自扩展进程

`TVUScreenRecordingClientSocketManager.mm:121-124`：

```objc
case RPSampleBufferTypeAudioMic:
///Comment: by alfred: Now use audioUnit to capture
//            _screenRecordingQueueManager->addDataToScreenRecordingQueue(sampleBuffer, TVUEXRecordingAudioMic, _screenRecordingQueueManager->sourceQueue[TVUEXRecordingAudioMic]);
    break;
```

对应地：

- 扩展进程的 mic 消费线程根本没创建：`TVUExtendRecordingQueueMananger.mm:176-179`（`pthread_create(..., startAudioThreadTask, ...)` 被注掉）。所以**线程 `EXRecordingAudioThread` 在当前基线下不存在**（只有 `EXRecordingVideoThread` 和 `EXRecordingAudioAPPThread` 是活的）。
- 主 App 接收侧 `TVUScreenRecordingFrameTypeAudioMic` 分支是空的：`MainViewController.mm:7682-7725`（整段注释）、`TVUIRLSDK.mm:443-447`（空 `case`）。

**结论**：屏录 mic 队列的数据全部由**主 App 进程内部**改道注入，入口是 `tvuSendAudioToScreenShare()`（见第四节）。扩展进程只负责 video + App 音频两路。

### 0.2 `TVUExtendRecordingQueueMananger` 在**扩展进程**，不在主 App

由 `TVUAnywhere.xcodeproj` 的 target 成员关系确认（`plutil` 解析 `project.pbxproj`）：

### 0.3 没有 `audioMix()` 这个方法

### 1.1 `SampleHandler`（`TVUScreenRecording/SampleHandler.m`）

`RPBroadcastSampleHandler` 子类，86 行，只做三件事：

### 1.4 `sendAudioSampleBuffer:frameType:`（`TVUScreenRecordingClientSocketManager.mm:256-412`）—— 封包

流程（App 音频路，Mic 分支代码在但不会被调用）：

1. `:258` 刷新 `last_audio_time_stamp`（供 `sendVideoSampleBuffer:` 的 0.3 s A/V 追赶判断用，`.mm:162`）。
2. `:260` 取 `pts = CMSampleBufferGetPresentationTimeStamp(sampleBuffer)`（`CMTime`，ReplayKit 域）。
3. `:264-283` 取 `CMBlockBuffer` 数据指针，`totalBytes == 0` 或出错则返回。
4. `:287` 选静态缓冲：`dataPointerApp` / `dataPointerMic`，两者都是 `int16_t[bufferSamples]`，`bufferSamples = 48000 * 8 = 384000`（`.mm:23-25`）→ 每个 768000 字节。
5. `:289` `memset(dataPointer, 0, bufferSamples)` —— ⚠️ 只清了 384000 字节（数组的一半，见第十节）。
6. `:291-299` `CMBlockBufferCopyDataBytes` 拷进静态缓冲。
7. `:301-303` 从 `AudioStreamBasicDescription` 读 `totalSamples = totalBytes / (mBitsPerChannel/8)`、`channels = mChannelsPerFrame`、`sampleRate = mSampleRate`。
8. `:306-314` **float → int16**（`kAudioFormatFlagIsFloat` 时，`*32767` 并 clamp）。
9. `:317-325` **big-endian → little-endian**（`kAudioFormatFlagIsBigEndian` 时逐 2 字节 swap）。
10. `:327` 自增 `audioAppIndex` / `audioMicIndex`（从 1 开始，`disconnectSocket` / `didEndWithError` 清零，`.mm:89`、`:152`）。
11. `:334-344` 按 `(channels, sampleRate)` 变化**惰性重建 `TVUFFmpegResample`**：
    ```objc
    src_sample_fmt = AV_SAMPLE_FMT_S16,  dst_sample_fmt = AV_SAMPLE_FMT_S16
    src_sample_rate = sampleRate,        dst_sample_rate = 48000
    src_nb_channels = channels,          dst_nb_channels = 1        // ← 降到单声道
    andSrcNBSample: 1024
    ```
12. `:346-351` `outData = malloc(totalBytes * 5)`，`convertor_feed_data:...andOutSize:&outSize andOutBuffer:outData`，包成 `NSData`。
13. `:352-356` 组包 → `TVUScreenRecordingDispatchDataWithAudioData(data, 1, 48000, pts, audioAppIndex)`。
14. `:358-365` `sendFrameOfType:TVUScreenRecordingFrameTypeAudioApp tag:PTFrameNoTag withPayload:payload`。
15. `:366` `free(outData)`。

**扩展进程发出的 App 音频规格**：48000 Hz / **1 声道** / S16LE / 长度 `outSize` **可变**（受 `swr_get_delay` 影响）。

### 1.5 协议头结构 & 字节序（`TVUScreenRecordingSocketProtocol.h`）

两层协议：Peertalk 的帧头 + 本工程的 payload 头。

**本工程 payload 头**（`:24-33`）：

```c
typedef struct TVUScreenRecordingFrame {
    uint32_t length;      // 载荷长度，htonl 网络序（唯一做字节序转换的字段）
    NSInteger index;      // 序号，主机序
    CMTime    pts;        // 结构体整体按主机序原样拷贝
    size_t    width;      // 主机序（音频路不填，为 0）
    size_t    height;     // 主机序（音频路不填，为 0）
    uint32_t  channel;    // 主机序（视频路不填，为 0）
    Float64   sampleRate; // 主机序（视频路不填，为 0）
    uint8_t   data[0];    // 柔性数组，紧跟其后
} TVUScreenRecordingFrame;
```

- **只有 `length` 做字节序转换**：发送 `frame->length = htonl(length)`（`:40` 视频 / `:56` 音频），接收 `frame->length = ntohl(frame->length)`（`MainViewController.mm:7586`、`TVUIRLSDK.mm:382`）。其余字段（含 `CMTime`、`NSInteger`、`size_t`、`Float64`）**全部主机序原样传**。同机同 ABI，所以可行，但结构体没有 `__attribute__((packed))`，隐含 padding 也一样靠双方同一编译器保持一致。
- 音频路和视频路用**同一个 struct**，各填自己那半字段：
  - `TVUScreenRecordingDispatchDataWithVideoData(data, width, height, pts, index)`（`:35-49`）→ 不填 `channel`/`sampleRate`
  - `TVUScreenRecordingDispatchDataWithAudioData(data, channel, sampleRate, pts, index)`（`:51-65`）→ 不填 `width`/`height`
  - 两者都用 `CFAllocatorAllocate` 一次性分配 `sizeof(header)+length`，`dispatch_data_create` 的析构块里 `CFAllocatorDeallocate`。
- 帧类型常量（`:18-22`）：`Video = 101`、`AudioApp = 102`、`AudioMic = 103`。
- 端口 `TVUScreenRecordingIPv4PortNumber = 2345`（`:16`），走 `INADDR_LOOPBACK`（`.mm:69` connect / `TVUScreenRecordingServerSocketManager.mm:50` listen）。
- **外部源索引 `TVUScreenRecordingSourceIndex = 100`**（`:15`）—— 屏录整条链路在编码器侧的身份标识，见第九节。

**分片**：本工程**不做应用层分片**。一个 ReplayKit sample buffer → 一个 payload（一次 `sendFrameOfType:`）。分片/重组由 Peertalk 的 `PTProtocol` 负责（`PTProtocol.h:7-11`：*"Each transmission is comprised by one fixed-size frame ... Each frame can have application-specific data of up to UINT32_MAX size"*）。Peertalk 帧头本身的字段布局与字节序**未确认**——仓库里只有 `Peertalk.framework` 预编译二进制 + headers，没有 `PTProtocol.m` 源码。

```objc
    if (dataposition >= framesize) break;

    if (pFramebuff->timestamp < 0 || pFramebuff->size == 0) {             // :288  只在开始填一个新 buff 时打时间戳

    pFramebuff->size += copydatasize;  dataposition += copydatasize;
```

要点：

- **只有填满 4096 字节的 frame 才对 `popFrame()` 可见**（`m_count++` 在 `size == capacity` 时才做）。
- 时间戳只在一个 buff 从空开始填时赋值，值 = 本次 `pushFrame` 的绝对 `frametime` + **本次调用内**的字节偏移换算（`/192` ms，整数截断）。**跨调用不累加**，与 `MainViewController.mm:7670-7675` 那段 2023-09-22 的注释一致（"摒弃以前累计采样点计算 pts 的算法"）。
- 残留的半满 buff 保留它先前的时间戳，下一次 `pushFrame` 续填，所以一个输出块的 pts 是"开始填它的那次 socket 帧"的 pts。

### 6.4 `mix()`（`.mm:590-626`）—— 归一化混音 + 软限幅

```objc
void TVUScreenRecordingQueueManager::mix(uint8_t **audioSourse, uint8_t *mix_data, int buffer_size, double coefficient)
{
    int const MAX = 32767;  int const MIN = -32768;
    double f = 1;  double output;
    for (int i = 0; i < buffer_size/2; i ++) {                 // 按 int16 逐样本
        double temp = 0;
        temp += (*(short *)(audioSourse[0] + i * 2));                  // mic：系数 1.0
        temp += ((*(short *)(audioSourse[1] + i * 2)) * coefficient);  // app：乘 coefficient
        output = (temp * f);
        if (output > MAX) { f = (double)MAX / (double)(output); output = MAX; }
        if (output < MIN) { f = (double)MIN / (double)(output); output = MIN; }
        if (f < 1) { f += ((double)1 - f) / (double)32; }              // 削波后 1/32 步长缓慢恢复
        *(short *)(mix_data + i * 2) = (short)output;
    }
}
```

### 8.2 各路来源与计算式

| 路 | 计算式 | 位置 | 时钟域 |

### 8.3 与视频对齐的三个机制

1. **扩展进程侧丢视频**：`sendVideoSampleBuffer:`（`ClientSocketManager.mm:161-164`）

   注释：*"录制过程中被打断（siri），video 不受影响，audio 会暂停，当恢复时，音视频不同步，需要将这一段时间内的 video 丢弃"*。
2. **主 App 侧强插 I 帧**：App 音频 pts 跳变 ≥0.3 s → `forceInsertKeyFrame`（`MainViewController.mm:7620-7629`、`TVUIRLSDK.mm:415-418`）。
3. **音频两路之间的 25 ms 对齐**：第 6.3 节。

**没有跨音视频的 pts 重锚**：两条链共用 ReplayKit 的 sample buffer PTS 域（App 音频、视频），而 mic 路的 pts 来自完全不同的时钟（`TVURecorder` / 外部源解码器 / DJI host-time）。混音输出取 **mic** 的 pts（`.mm:541`），单路降级也 mic 优先（`.mm:474`）。**mic 与视频之间没有对齐机制**——只有 mic 与 App 音频之间有 25 ms 门限。这是本链路最值得运行时验证的一点。

## 十一、顺手发现的代码问题（只记录，未改动任何源码）

按可疑程度排序。

1. **`sendAudioSampleBuffer:` 错误路径重复释放** —— `TVUScreenRecordingClientSocketManager.mm:266`、`:282`、`:297` 三处 `CFRelease(sampleBuffer)` 后 `return`，但调用方 `handleAudioApp()`（`TVUExtendRecordingQueueMananger.mm:347-348`）返回后无条件调 `resetWorkQueueNode(node)`，其内部 `.mm:118-120` 又 `CFRelease(node->param.data)` —— 同一个 sample buffer 被释放两次。`handleAudio()`（`.mm:337-338`）同理（该路径当前不可达）。
2. **`data_mix` 只分配一次且不随块长增长** —— `TVUScreenRecordingQueueManager.mm:532`：
   ```objc
   static uint8_t *data_mix = (uint8_t *)malloc(mic_node->param.dataSize * 2);
   ```
   `static` 局部变量的初始化只执行一次，用的是**第一个** mic 节点的 `dataSize`。之后若 mic 块长变大（DJI 路 `pcmLength` 可变、切换音源），`mix()` 会越界写。当前内置 mic / Accsoon 恒为 4096（分配 8192，有 2× 余量），DJI 路是风险点。
3. **`gain_data` 每帧 realloc** —— `.mm:258-266`：
   ```objc
   if (gain_size == 0) { gain_size = param->dataSize * 2; gain_data = malloc(gain_size); }
   else if (gain_size != param->dataSize) { gain_size = param->dataSize * 2; gain_data = realloc(...); }
   ```
   第二个条件把 `gain_size`（= 2×dataSize）和 `param->dataSize`（= 1×）比 —— 首帧之后**永远不相等**，于是每个 mic 帧都走 `realloc`。意图应是 `gain_size != param->dataSize * 2`。功能上无害（尺寸算对了），但音频线程每帧一次 realloc。
4. **`memset` 长度算错** —— `TVUScreenRecordingClientSocketManager.mm:289`：`memset(dataPointer, 0, bufferSamples)`，而 `dataPointer` 指向 `int16_t[bufferSamples]`（768000 字节），只清了 384000 字节。因为紧接着就 `CMBlockBufferCopyDataBytes` 覆盖有效区，实际无害。
5. **`getPcmDB` 只取正向峰值** —— `TVUAnywhereTool.h:288-292` 的峰值循环 `if (nMax < nCurr) nMax = nCurr;`，`nCurr` 是有符号 `short`，全负样本块（或负向为主）会得到 `nMax < 1` → 直接判 `-60 dB` → coefficient = 1.00（不压 App 音频）。这是全仓库共用的实现（另外 4 处混音器也用它），不是屏录特有。
6. **`monoConvertToStereoWithMonoAudio:` 尾部越界读 1 字节** —— `TVUAnywhereTool.mm:1103-1113`，`i` 遍历到 `mono_audio_size-1`，偶数分支会读 `mono_audio[i+1]`；当 `mono_audio_size` 为偶数时最后一次偶数 `i = size-2`，读 `size-1`，恰好不越界。奇数长度会越界读 1 字节（音频块恒为偶数，实际不触发）。
7. **`TVUScreenRecordingQueueManager::endThread()` 无调用方** —— `.mm:319-340`，两条 pthread 随进程存活；`getAppAudioQueueFirstNodePts()`（`.mm:666-675`）同样无调用方（`getCurrentNodePts()` 才是实际用的那个）。
8. **`tvuSendAudioToScreenShare` 四份 `static` 副本** —— 见第四节。其中 `TVUScreenRecordPcmContractor.mm:121` 那份是纯死代码（同 TU 无调用者，且 `static` 外部不可见）。改动混音闸门逻辑必须同步改 4 处。
9. **`TVUScreenRecordingFrame` 结构体无 `packed`** —— `SocketProtocol.h:24-33` 含 `uint32_t / NSInteger / CMTime / size_t / uint32_t / Float64` 混排，靠隐含 padding 传输。两侧同编译器同 ABI 才安全；`length` 之外的字段不做字节序转换。

## 十二、不确定 / 需运行时验证的点

1. **Peertalk 帧头的确切布局与字节序** —— `Peertalk.framework` 只有预编译二进制 + headers，仓库内**没有** `PTProtocol.m` / `PTChannel.m` 源码。`PTProtocol.h:7-11` 只说"固定大小帧 + 版本号 + 类型 + tag + payload"。上游开源实现对四个头字段都做 `htonl`，但**本基线无法从代码确认**。
2. **ReplayKit `RPSampleBufferTypeAudioApp` 的实际格式与块长** —— 代码完全动态读 `AudioStreamBasicDescription`（采样率、声道、float/int、大小端都有分支），说明作者见过多种组合。具体设备/iOS 版本上的取值需真机抓。
3. **重采样后每包 `outSize`** —— `TVUFFmpegResample::convertor_feed_data` 的输出长度由 `swr_get_delay` + `av_rescale_rnd` 决定（`TVUFFmpegResample.mm:230-231`），逐包变化。这是 PCM 分包器存在的理由，但具体分布未确认。
4. **DJI 路 `pcmLength` 是否恒为 4096** —— `RTMPIngestController.mm:376-388` 直接透传解码器输出长度，无校验、无重切。若不等于 4096，会导致：(a) 与 App 队列块长不一致 → `mix()` 用 mic 长度读 app 缓冲（长了越界读 app、短了漏混）；(b) 触发第十一节第 2 条的 `data_mix` 越界。需实测 `TVUIRLAudioDecoder` 的输出粒度。
5. **单路模式的首秒行为** —— 第 5.3 节推导：`mixType == 1` 或 `2` 时，`encodeAudio()` 要等 `current - last_audio_mix_time > 1000` 才走单路分支。`last_audio_mix_time` 在 `stopThread()`（`.mm:316`）清零、`encodeAudio()` 首次进入时置为 `current`（`.mm:451-453`）。推导结论是投屏开始后约 1 秒内单路音频被空转丢弃，需实测确认是否真有可听的开头静音。
6. **mic 与视频之间的对齐** —— 第 8.3 节：混音输出 pts 取 mic（来自 `TVURecorder`/外部源/DJI 时钟），视频 pts 来自 ReplayKit 时钟，两者之间**代码里没有任何重锚或补偿**。25 ms 门限只管 mic↔App 音频。实际 A/V 偏移量需真机测量。
7. **`isReceivingFrame = YES` 与 `startThread()` 之间的窗口** —— 第 9.1 节：`.mm:125` 置位早于 `.mm:135` 的 delegate 回调。窗口时长（同一函数内，几微秒？）与丢帧数量需实测；理论上只丢窗口期内到达的 mic 帧。
8. **`TVUExtendRecordingQueueMananger` / `TVUScreenRecordingClientSocketManager` 在主 App 与 `TVUIRLSDK` target 里的用途** —— 两个文件确实编进了主 App，但主 App 唯一的调用路径是 `TVUIRLSDK.mm:250-270`（供 IRL 产品的扩展经由 SDK 反向调用）。TVUAnywhere 自己的扩展 target 是独立编译的那一份。是否存在其他隐式使用路径未穷尽验证。
9. **`aacEncoder::doencode()` 是否真的完全不可达** —— 仓库内 `pushFrame` / `pushOnechannelFrame` 的所有调用点都被注掉（`TVURecorder.mm:623/625/850/852/2290`），且 `grep` 未发现其他调用方。但 `startEncode()` 仍在 `TVUAnywhere.mm:802`、`:860` 被调，线程在跑。若有通过其他 product（`TVUPartyline` / `TVUIRL` 独立工程）的调用路径，本次未覆盖。
