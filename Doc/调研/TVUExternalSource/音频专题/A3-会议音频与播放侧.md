## 1. 上行：`pushAudioData:andSampes:andTimestamp:` 的实现

### 1.1 参数语义

实现在 `TVUAnywhereSDK/TVUAgora/TVURTCModule/RTCLogic/TVUIntegrateAgoraTools.mm:1993-2041`：

```objc
// :2032-2040
int64_t prsentTimeMS = (int64_t)(timestamp * 1000);
int64_t current_timestamp = [TVUHostTimer convertToUTCTimestampWithSystemPTS:prsentTimeMS];

[self.agoraKit pushExternalAudioFrameRawData:data
                                     samples:samples * 2 // samples = data.length / sizeof(int16_t)
                                  sampleRate:48000
                                    channels:2
                                     trackId:self.audioTrackId
                                   timestamp:current_timestamp];
```

- **`andSampes` = 每声道采样点数**（不是总数）。三个调用点全部传
  `param->size / (2 * param->channel)`：`TVUAudioEncoderManager.mm:237`、
  `aacEncoder.mm:212`、`aacEncoder.mm:342`。方法内部再 `* 2` 补上硬编码的 2 声道，
  交给 Agora 的就是**总 int16 个数** = 字节数 / 2。行内注释
  `samples = data.length / sizeof(int16_t)` 描述的是 Agora 侧的语义，不是本方法入参的语义。
- **`sampleRate` / `channels` 硬编码 48000 / 2**（`:2037-2038`），不看入参也不看实际数据。
  单声道数据进来会算错，靠上游保证：`TVUAudioEncoderManager.mm:191-198` 在
  `isJoined || enableEncoding` 时把单声道升成双声道；`aacEncoder.mm:325-330` 在
  Partyline SDK 路径上做同样的事。
- **没有格式转换**。方法体内只做 pts 换算，不做重采样、不做声道转换、不做拷贝。
  唯一的"转换"是上游做的单→双声道（`monoConvertToStereoWithMonoAudio:`）。

### 1.5 WebRTC VOIP 上行入口

入口方法：**`-[TVURecorder pushWebRTCAudioData:dataSize:timestamp:]`**
（`TVUAnywhereSDK/TVUAudioCapture/TVURecorder.mm:2357-2402`）。

### 1.6 RTIL VoIP 上行入口

入口方法：**`-[TVURTILVoIPManager pushAudioData:dataSize:channels:sampleRate:timestamp:]`**
（`TVUAnywhereSDK/TVUAgora/TVURTCModule/RTCLogic/TVURTILVoIP/TVURTILVoIPManager.mm:115-125`，
声明 `TVURTILVoIPManager.h:85`）。纯转发到 Engine。

`TVURTILVoIPEngine.mm:144-159`：

```objc
TVURTILVoIPChannel *channel = self.channels.firstObject;
if (channel.mute) { return; }
[self.agoraKit pushExternalAudioFrameRawData:data
                                     samples:dataSize / (sizeof(int16_t))   // :154 总样本数
                                  sampleRate:sampleRate                     // 透传硬件采样率
                                    channels:channels                       // 透传硬件声道
                                     trackId:channel.audioTrackId
                                   timestamp:timestamp];                    // 透传 CMClock 秒
```

和 Partyline 的三点不同：
1. **不做单/双声道归一，不硬编码 48k/2**，直接把 `recorder->mRecordeAudioSamplerate` /
   `mRecordeAudioChannel` 透传（`TVURecorder.mm:557-558` / `:785-786`）。
2. **`samples` 是总样本数**（`dataSize / 2`），不是每声道；语义与 Partyline 那条**相反**。
3. **timestamp 不经 `TVUHostTimer` 换算**，直接是 `RecordCallback` 里的
   `nowTime = CMTimeGetSeconds(CMClockGetTime(CMClockGetHostTimeClock()))`
   （`TVURecorder.mm:392-394`；AudioQueue 侧同理 `:719`）——**单位是秒**，
   而 Partyline 那条传给 Agora 的是毫秒。

> ⚠️ 两条路都调 `pushExternalAudioFrameRawData:...timestamp:`，一条给毫秒一条给秒。
> 这是可疑点，但没有找到把 RTIL 的 timestamp 再换算的代码，如实记录。

**RTIL 与 Partyline 共用同一个 AgoraRtcEngineKit**：
`TVURTILVoIPChannel.mm:229-231` `- (AgoraRtcEngineKit *)agoraKit { return [[TVUIntegrateAgoraTools getInstance] agoraKit]; }`
（Engine 侧 `TVURTILVoIPEngine.mm:207` 同）。区别只在 `trackId`：
Partyline 用 `TVUIntegrateAgoraTools.audioTrackId`（建于 `:486`），
RTIL 用 `TVURTILVoIPChannel.audioTrackId`（建于 `:61` → `createAudioTrack` `:213-219`）。
两个 track 的 `AgoraAudioTrackConfig.enableLocalPlayback = NO`
（`TVUIntegrateAgoraTools.mm:485`、`TVURTILVoIPChannel.mm:216`），所以本地不会自己听到自己。

### 2.4 WebRTC 下行：`rtcResample()` 与 `getPlayoutAudioByBufferRef`

WebRTC 的 playout **不是回调推给我们，是我们自己开线程拉**。

线程：ctor 里就建（`AudioPlayer.mm:291` `pthread_create(&rtc_thread, NULL, startThreadTask, this)`），
`threadToSuspend` 初值 `true`（`:287`）。`startThreadTask`（`:1045-1053`）→

### 2.6 `TVUAudioPlayerQueueManager::addData` → 扬声器

类定义 `TVUAnywhereSDK/TVUAudioPlayer/TVUAudioPlayerQueueManager.h`：
`kTVUAduioPlayerQueueNodeSize = 8`（`:11`，注意 `Aduio` 拼错）、
`addData(uint8_t*, int)`（`:41`）、`deQueue(TVUAudioPlayerQueue*)`（`:42`）、
`getWorkQueueSize()`（`:43`）、`resetNode()`（`:44`）、
`resetAllWorkQueueNode()`（`:45`）、`resetFrontNode()`（`:46`）。
**没有 getData/popData**，读就是 `deQueue(work_queue)`，读完必须 `resetNode` 还回去。

结构是 work / free 两条侵入式单链表共享 8 个节点的固定池（ctor `.mm:25-44`）。
work 队列 FIFO 尾插（`.mm:99-100`），free 队列 LIFO 头插（`.mm:86-87`）。
两把独立 `pthread_mutex_t`（`work_mutex` / `free_mutex`），`static mutex m_mutex` 只是单例锁。

`addData`（`.mm:46-63`）先从 free 池取节点，取不到就**丢当前帧**并 log（`.mm:50-53`）；
`node->data = malloc(size); memcpy; enQueue(work_queue, node)`。
`enQueue` 本身**没有任何容量检查**，8 个节点就是全部背压。

> ⚠️ `TVUAudioPlayerQueueManager.mm:54-57`：`size <= 0` 时已经从 free 队列摘下来的节点
> **既不归还也不 free**，池子永久 8→7→…→0，归零后 VoIP 播放彻底静音。
> 对比 `resetNode`（`.mm:147-161`）是会归还的。

全仓库**只有 `AudioPlayer.mm` 用这个类**（`grep -rn TVUAudioPlayerQueueManager` 的另一处
`TVUPartylineScreenCaptureManager.mm:133` 只是拿这个字符串当 log4cplus category 名）。

| 角色 | 位置 |
|---|---|
| 生产 | `AudioPlayer.mm:1146`（重采样分支）、`:1158`（直通分支），都在 `rtcResample()` |
| 消费 | `:620`（AudioUnit VoIP）、`:884`（AudioUnit Agora）、`:1220`（AudioQueue Agora）、`:1297`（AudioQueue WebRTC） |
| 丢弃 | `:856` `resetFrontNode()`（Partyline 静音扬声器时只丢不放）、`:340`/`:346` `resetAllWorkQueueNode()`（切 streamType 时清空） |

完整出声链路见 §7 的调用链清单。

### 2.7 混进直播流的两个队列

`TVUWebRTCMixQueueManager` / `TVUPartyLineMixQueueManager` 是**同一份代码复制两遍**


> 升声道后 `rtc_size = 4096`，`max(4096, 2048) = 4096`，恰好对。但如果哪天

## 4. 三者互斥关系

### 4.1 结论：**代码里没有互斥**

没有找到任何"Partyline 已进会就禁止 VoIP"或反向的守卫：
- `TVURTILVoIPManager -voipStartWithParam:`（`TVURTILVoIPManager.mm:232`）只检查参数合法性
  （`checkErrorStartParam:`）和自身状态（`:244-245` 已 Join / Joining），**不看 Partyline，不看 WebRTC**。
- `TVUIntegrateAgoraTools -joinChannelWithType:withIsJoinBySwitchingParty:`（`:458`）里没有
  `voipIsCalling` / `[[TVURTILVoIPManager manager] isRunning]` 检查。
- `TVUWebRTCManager -tvuCallRequest:type:`（`:307`）里也没有 Partyline 检查。

三者用的是两套完全独立的传输栈（Agora RtcEngineKit ×1 共享给 Partyline + RTIL；
WebRTC ×1 独立），互不冲突。播放侧靠 `isPlayAgoraAudio`（§2.2）把 Agora 提到优先，
WebRTC 的声音在 Agora 分支里作为 `voip_data` 与 `agora_data` 二路混音
（`AudioPlayer.mm:906-927` / `:1253-1274`）—— **恰恰说明设计上就允许同时开**。

### 4.2 生产侧会不会两家同时塞？会

把 §2.7 生产侧的条件排成真值表，两个队列同时被生产的充要条件是：

```
enableEncoding && enableMixVoip && voipIsCalling            // WebRTC 队列
&& enableMixPartyLine && (agoraJoined || RTILVoIPRunning)   // PartyLine 队列
&& (agoraState != Joined || !enableMixPartyLine)            // WebRTC 队列的第二个条件
```

第 1、3 行要求 `agoraState != Joined`（因为 `enableMixPartyLine` 已为真），
第 2 行于是必须靠 `RTILVoIPRunning` 满足。即：

> **RTIL VoIP 在跑 + WebRTC VoIP 在通话 + 两个 mix 开关都开 + 正在直播/录制**
> → 两个混音队列同时被填。

而消费侧（`TVUAudioEncoderManager.mm:286-316`，主 App 分支）在这个组合下：
`enableMixPartyLine && agoraState == Joined` 为假（未进 Partyline）→ 走 else →
`enableMixVoip && voipIsCalling` 为真 → **只消费 WebRTC 队列**，
`:306` 的 RTIL 分支是 `else if`，永远轮不到。

结果：**PartyLine 混音队列只进不出**，涨到 `kTVUPartyLineMixQueueNodeSize = 10`
（`TVUPartyLineMixQueueManager.h:11`）后 `addData` 开始丢帧并刷 log
（`TVUPartyLineMixQueueManager.mm:52-55`）。清空只有三处被动时机：
`TVURecorder.mm:381-382`（首帧）、`TVURecorder.mm:752-753`（audio/video not ready）、
以及各自的 `resetAllWorkQueueNode()`。

> 这是**生产/消费口径不一致**导致的队列淤积，不是崩溃。是否真能出现取决于
> RTIL VoIP 与 WebRTC VoIP 能否被业务同时拉起 —— 列入待验证。

### 4.3 一个更早的分歧：flavor 宏

`TVU_HIT_ME` / `_TVUSDKANYWHERE` 分支（`TVUAudioEncoderManager.mm:275-284`）
**只认 `enableMixVoip`，从不读 `enableMixPartyLine`**。
所以在 SDK flavor 上，PartyLine 混音队列有人塞（`AudioPlayer.mm:903`/`:1249` 不受 flavor 宏限制）
但**永远没人消费**。同样只是淤积 + 丢帧。

### 5.2 `subcontractWithInBuffer:` 怎么切 2048 字节块

`TVUAnywhereSDK/TVUTools/TVUResample/TVUFFmpegResample.mm:291-329`：

```objc
#define TVUSUBCONTRACTSAMPLES 1024                                    // :291

int needPacketSize = mBytesPerFrame * TVUSUBCONTRACTSAMPLES;          // :298
static int packetSize = needPacketSize;                               // :299  ⚠️ static
if (!pcm_buffer_temp) pcm_buffer_temp = malloc(packetSize);           // :300-302
if (packetSize != needPacketSize) { packetSize = needPacketSize; realloc(...); }  // :303-306

memcpy(pcm_buffer + pcm_buffer_size, in_buffer, in_zize);             // :307
pcm_buffer_size += in_zize;                                           // :308

while (pcm_buffer_size >= packetSize) {                               // :314
    memcpy(pcm_buffer_temp, pcm_buffer, packetSize);                   // :316
    sample_total += packetSize / mBytesPerFrame;                       // :317
    if (isAudioFirstF == false) { isAudioFirstF = true; sample_total = 0; }   // :318-321
    Float64 pts_d_f = 1.0 / (Float64)outDefaultSampleRate * sample_total;     // :322
    hadleBlock(pcm_buffer_temp, pts_d_f, packetSize);                  // :323
    memmove(pcm_buffer, pcm_buffer + packetSize, pcm_buffer_size - packetSize);  // :325
    pcm_buffer_size -= packetSize;                                     // :326

```

调用方传 `mBytesPerFrame = (kTVUMBitsPerChannel/8) * kTVUAudioChannel = (16/8)*1 = 2`
（`AudioPlayer.mm:1144`；常量 `Transmitter/TVUConst.h:414-415`）。
所以 `needPacketSize = 2 * 1024 = 2048`，正好是播放器要的块。

**PTS 语义**：`subcontract` 回调里的 `pts` 是**从第一块起算的相对秒数**
（`sample_total / outDefaultSampleRate`，第一块强制归零 `:320`），
不是绝对时间。`AudioPlayer.mm:1145-1154` 的 block **把这个 pts 丢掉了**——
只用 `out_buffer` / `outSize`，播放侧不需要 pts。
IFB 路径（`AudioPlayer.mm:1498-1500`）才用到：`m_PCMQueue.enQueue(out_buffer, outSize, timestamp + pts)`。

> ⚠️ `packetSize` 是 **`static`**（`:299`），跨实例共享。`AudioPlayer` 有两个
> `TVUFFmpegResample` 实例（`rtcResample` 里的 `static ffmpegResample` `:1104`，
> 和 IFB 的成员 `resample` `AudioPlayer.h:199`），
> `TVURecorder`、`TVUExternalSourceParse` 等还有更多。两者 `mBytesPerFrame` 都是 2，
> 所以目前无碍；若有一个实例用不同 `mBytesPerFrame`，会互相踩。

### 6.4 `mix()` 算法

`AudioPlayer.mm:1645-1681`（声明 `AudioPlayer.h:137`）：

```objc
void AudioPlayer::mix(uint8_t **audioSourse, uint8_t *mix_data, int buffer_size, double coefficient)
{
    int const MAX = 32767;  int const MIN = -32768;
    double f = 1;                                     // :1651  ⚠️ 每次调用重置为 1
    for (int i = 0; i < buffer_size/2; i++) {
        double temp = 0;
        temp += *(short *)(audioSourse[0] + (i << 1));                    // :1657-1658  源0 原样
        temp += ((*(short *)(audioSourse[1] + (i << 1))) * coefficient);  // :1660-1661  源1 乘系数
        double output = temp * f;                                        // :1663
        if (output > MAX) { f = (double)MAX / output; output = MAX; }     // :1665-1669
        if (output < MIN) { f = (double)MIN / output; output = MIN; }     // :1670-1674
        if (f < 1)        { f += (1 - f) / 32; }                         // :1675-1678  释放
        *(short *)(mix_data + (i << 1)) = (short)output;                  // :1679
    }
}
```

即经典的"归一化混音 + 软限幅"：`f` 是动态增益，一旦削顶就按比例压下来，
然后每个样本回升 `(1-f)/32`（约 32 样本的 release）。
**`f` 是局部变量，每次调用重置为 1**，所以 release 状态不跨块保留 —— 块边界会有增益跳变。

`coefficient` 只作用于 `audioSourse[1]`。三个调用方：

| 调用方 | `source_data[0]`（不加权） | `source_data[1]`（乘 coefficient） | coefficient |
|---|---|---|---|
| `AudioPlayer::audioUnitPlayWithBufferListForVoip` `:649` | `rtc_data`（VoIP 下行） | `vfb_data`（视频回传音频） | `tvuGetVolumeScale(getPcmDB(rtc_data, 2048))` |
| `AudioPlayer::audioUnitPlayWithBufferListForAgora` `:913`；`handleTVUAgoraAudioOutputBuffer` `:1260`；`handleTVUWebRTCAudioOutputBuffer` `:1328` | `agora_data` / `rtc_data`（会议下行） | `voip_data` / `vfb_data` | 同上，按会议声的 dB 动态压另一路 |
| `TVUWebRTCMixQueueManager::voipMixWith` `:87` | `rtc_data`（VoIP 下行升双声道） | `source`（采集 PCM） | **`1.0` 固定** |
| `TVUPartyLineMixQueueManager::partyLineMixWith` `:88` | `rtc_data`（Agora 下行升双声道） | `source`（采集 PCM） | **`1.0` 固定** |

**播放侧用动态 ducking（会议声大就压回传声），混进直播流时不 ducking（1:1）。**

`mix()` 有个**共用陷阱**：只读 `audioSourse[0]` 和 `audioSourse[1]` 两路，
按 `buffer_size/2` 个 int16 遍历。两个混音队列传的 `*outSize` 是
`max(sourceSize, node->size)`（§2.7），而 `*output` 只分配了 `sourceSize + rtc_size`，
`rtc_data` 只有 `node->size * 2` 字节 —— 若 `*outSize > rtc_size`，
`audioSourse[0]` 会**读越界**。目前 4096 == 4096 恰好不越界。

## 8. 顺手记下的问题（源码级，非本次任务结论）

按发现顺序，都在本文覆盖的代码里：

1. **`AudioPlayer.mm:891` / `:1227`：`||` 写成了本该是 `&&`**
   ```objc
   if (audiodataref != NULL || audiodataref->length() == kTVUAudioPlayerDataByteSize || audiodataref->data() != NULL)
   ```
   `audiodataref` 为 NULL 时第一项为假，第二项立刻空指针解引用。

2. **`AudioPlayer.mm:890` / `:1226`：变量遮蔽导致 `AudioDataBuff` 泄漏**
   内层 `AudioDataBuffRef audiodataref = ...` 遮蔽了外层（声明于 `:834` / `:1195`），
   外层永远是 NULL，`:931` / `:1279` 的 `delete audiodataref` 永不执行。
   `:1214-1219` 的 ITA-1141 注释说的正是这类 bug（当时只修了 `node`，没修 `audiodataref`）。

3. **`AudioBuffer buffer = ioData->mBuffers[0];` 是值拷贝**
   （`AudioPlayer.mm:586` / `:701` / `:825`，`TVURecorder.mm:677`），
   随后的 `buffer.mDataByteSize = mDataByteSize;`（`:587` / `:702` / `:826` / `TVURecorder.mm:679`）
   **写不回 `ioData`**。`memcpy` 到 `buffer.mData` 仍然生效（指针），所以有声音；
   但 `TVURecorder.mm:688-689` 的 `TVUSpeechManager sendAudioData:size:` 读的是
   `ioData->mBuffers[0].mDataByteSize`，拿到的是 CoreAudio 留下的值。

4. **`TVUAudioPlayerQueueManager.mm:54-57`：`size <= 0` 时节点泄漏**，池子会被逐步耗尽（§2.6）。

5. **`AudioPlayer.mm:1049` 线程名与外部源混音线程重名**（§2.4）。

6. **`kTVUWebRTCAudioDataByteSize`(50) 与 `kTVUAudioPlayerDataByteSize`(51) 必须相等但无约束**（§2.5）。

7. **`TVUFFmpegResample.mm:299` 的 `packetSize` 是 `static`，跨实例共享**（§5.2）。

8. **`TVUIntegrateAgoraTools.mm:1992` `first_audio_frame_pts` 死变量**。

9. **RTIL VoIP 与 Partyline 传给同一个 Agora API 的 timestamp 单位不同**（秒 vs 毫秒，§1.6）。

10. **两个混音队列的 `*outSize = max(sourceSize, node->size)` 靠数值巧合成立**（§2.7 / §6.4）。
