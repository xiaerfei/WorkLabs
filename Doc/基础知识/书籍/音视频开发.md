# 第1章 音视频基础概念

## 1.1 声音的物理性质

- **声音**：物体振动产生的压力波（纵波）
- **三要素**：
  - 频率（音高）: 频率越高波长越短，衰减越快
  - 振幅（响度）: 用分贝(dB)衡量
  - 波形（音色）: 不同介质产生不同波形
- **听力范围**: 20Hz~20kHz，对3~4kHz最敏感
- **等响曲线**: 描述等响条件下声压级与频率关系；声压较低时听觉频率特性不均匀，80~90dB时较均匀
- **传播介质**: 空气、液体、固体；真空中无法传播；声速：空气340m/s，蒸馏水1497m/s，铁棒5200m/s
- **回声**: 声音反射；两次声音时差 < 80ms 无法分辨
- **共鸣**: 同频率物体振动，证明声音传播是能量传播

## 1.2 数字音频

- **采样**: 时间轴数字化，采样频率 > 信号最高频率的2倍（奈奎斯特定理）。CD音质常用44.1kHz（每秒44100次）
- **量化**: 幅度轴数字化，如16bit表示一个采样（范围-32768~32767，共65536级）
- **编码**: 按格式存储采样和量化数据，如PCM
- **PCM参数**:
  - 量化格式: 16bit
  - 采样率: 44100Hz
  - 声道数: 2
- **CD音质数据量计算**:
  - 比特率 = 44100 * 16 * 2 = 1411200 bps ≈ 1378.125 kbps
  - 1分钟大小 = 1378.125 * 60 / 8 / 1024 ≈ 10.09 MB
- **分贝**: 无量纲单位，N = 10*lg(A1/A0) 或 20*lg(...)

## 1.3 音频编码

- **压缩原理**: 去除冗余信号（人耳听觉范围外 + 被掩蔽的信号）
- **分类**:
  - 无损压缩: 完全复原
  - 有损压缩: 丢失信息，压缩比越小失真越大
- **常见格式**:
  - WAV: PCM加44字节头部，无损，音质好，中间文件/素材
  - MP3: 中高码率(≥128kbps)听感接近WAV，兼容性好，音乐欣赏
  - AAC:
    - LC-AAC: 中高码率(≥80kbps)
    - HE-AAC(AAC+SBR): 中低码率(≤80kbps)
    - HE-AACv2(AAC+SBR+PS): 低码率(≤48kbps)
    - 小于128kbps表现优异，视频常用音频编码
  - Ogg: 低码率下音质优于MP3，免费，兼容性不够好，语音聊天场景

## 1.4 图像的物理现象

- **三原色光**: 红(R)、绿(G)、蓝(B)无法分解，等量相加得白光
- **屏幕显示**: 手机自发光，每个像素由R、G、B三个子像素组成

## 1.5 图像的数值表示

### 1.5.1 RGB表示

- 浮点: 0.0~1.0 (OpenGL ES)
- 整数: 0~255 或 00~FF
  - RGBA_8888: 32bit/像素
  - RGB_565: 16bit/像素 (R:5bit, G:6bit, B:5bit)
- **位图大小**: 1280x720 RGBA_8888 = 1280*720*4 = 3,686,400 B ≈ 3.52 MB
- 因数据量大，需压缩(JPEG等)，但视频需考虑时域冗余

### 1.5.2 YUV表示

- **Y: 亮度(Luminance)**; **U(Cb), V(Cr): 色度**
- 优势: 只需极少频宽；兼容黑白电视(Y信号即可)；亮度与色度分离
- 常用采样格式: **4:2:0**
  - 水平/垂直方向色度采样率均为2:1
  - 8x4 图片仅需 48 字节
- 1280x720 YUV420P 一帧大小:
  - Y: 1280*720 = 921600
  - U: 1280*720/4 = 230400
  - V: 1280*720/4 = 230400
  - 总计 = 1382400 B ≈ 1.318 MB
- 90分钟电影(24fps) 数据量 ≈ 1.318MB * 24 * 60 * 90 ≈ 166.6 GB (必须压缩)

### 1.5.3 YUV与RGB转换

- 标清(601标准) 与 高清(709标准) 转换公式不同
- iOS摄像头采集YUV后可通过CVBufferGetAttachment获取YCbCrMatrix 决定使用哪种矩阵

## 1.6 视频编码方式

### 1.6.1 视频编码

- **冗余信息**:
  - **时间冗余**: 帧间预测编码（运动补偿、运动估计、运动表示）
  - **空间冗余**: 帧内预测编码
- **标准**:
  - MPEG-1(VCD), MPEG-2(DVD), MPEG-4 AVC(流媒体主流)
  - ITU-T: H.261, H.262, H.263, H.264
  - H.264 采用多参考帧、多块类型、整数变换、帧内预测等，压缩性能大幅提升

### 1.6.2 编码概念

1. **IPB帧**:
   - **I帧**: 帧内编码帧，关键帧，可独立解码，去除空间冗余，压缩比约6:1
   - **P帧**: 前向预测编码帧，参考前面I或P帧，去除时间冗余
   - **B帧**: 双向预测内插编码帧，参考前后帧，进一步提高压缩效率
2. **IDR帧**: 特殊的I帧，强制解码器清空参考帧缓冲区，后续帧不再参考该IDR之前的帧，用于随机访问点
3. **PTS与DTS**:
   - DTS (Decoding Time Stamp): 解码时间戳
   - PTS (Presentation Time Stamp): 显示时间戳
   - 无B帧时PTS=DTS；有B帧时两者不同
4. **GOP**: 两个I帧之间的图片组，gop_size越大画面质量越好，但解码端需从I帧开始才能正确解码。使用B帧可节省空间，节省的空间可更多保存I帧以提升画质。

### 关于 IDR 帧

> IDR 只代表解码不依赖前面的帧，没有要求它是后续第一个显示。把 IDR 当成首帧显示是个普遍的误解，只是在常见的码流里是成立的。标准测试流集合中，一堆特殊参考结构的码流，用来验证解码器是否严格符合标准。

1. **IDR 帧的核心定义：解码刷新，与显示顺序无关**

   在 H.264/AVC 标准中，IDR 帧（Instantaneous Decoding Refresh）的唯一定义是：
   - 解码器在遇到 IDR 帧时，会立即清空所有已存储的参考帧（DPB，Decoded Picture Buffer）。
   - 在解码顺序上，IDR 帧自身以及它之后的所有帧，都不能参考 IDR 帧之前的任何帧。

   这就是"IDR 只代表解码不依赖前面的帧"的本意：它只定义了解码依赖关系的断点，并没有对显示顺序做任何强制。

2. **"显示顺序" vs "解码顺序"是两套独立的时序**

   - **解码顺序**：码流里帧的实际排列顺序，也就是解码器拿到一帧就解码一帧的那个顺序。
   - **显示顺序（POC，Picture Order Count）**：帧最终被播放时的时间先后。

   IDR 帧强制切断的是解码依赖，但允许在显示顺序上出现"反常"情况，比如：

   - 解码顺序：IDR → B → P
   - 显示顺序：B（显示时间更早）→ IDR → P

   其中：
   - 这帧 B 的解码发生在 IDR 之后；
   - 它的显示时间却早于 IDR；
   - 因为 IDR 已经清空了前面的参考帧，所以这帧 B 只能以 IDR 及后续帧作为参考，不能参考 IDR 之前的任何帧。

   这种帧在 HEVC 里被明确归类为 RADL（Random Access Decodable Leading）图片，在 H.264 里也完全合法。从用户的角度看，IDR 帧并不是码流播放时"第一个出现的画面"。

3. **为什么人们普遍把 IDR 当成"首帧显示"？**

   因为在绝大多数现实码流（尤其是流媒体、网络视频）里：
   - 编码器为了简单、兼容性好，很少在 IDR 前面放显示更早的 B 帧；
   - 通常是把 IDR 对齐到一个画面组的显示起点，形成"封闭 GOP"，让 IDR 既是解码随机访问点，也是显示随机访问点。

   久而久之，很多开发者、学习者就把"IDR = 显示首帧"当成了定义本身，而这其实只是常见做法，不是标准强制。

4. **标准测试流里的"特殊参考结构"，正是为了纠正这种误解**

   在 H.264 的符合性测试流（如 JVT 的 conformance bitstreams）、H.265 的 JCT-VC 测试流里，都有专门设计的码流，其特征是：
   - IDR 帧之后紧跟着显示时间更早的前置 B 帧（leading B pictures）；
   - 存在 CRA（Clean Random Access）或 BLA（Broken Link Access）等不同随机访问点，搭配各种可解码/不可解码前置帧；
   - 一些码流中，某些帧解码需要使用 IDR 清空之前的参考帧规则才能正确处理。

   这些流的目的，就是验证解码器是否严格按"解码依赖"规则实现，而不是偷懒假设"第一帧解码的就是第一帧显示的"。如果一个播放器或解码器把 IDR 当作显示首帧来硬切，遇到这类合规码流就会出问题——跳帧、花屏、甚至崩溃。

**总结**：IDR 的核心语义是"解码依赖的断点"，而不是"显示顺序的起点"。它是否同时是显示首帧，完全取决于编码结构，标准从未要求，只是大多数日常码流恰好如此。
