# 原文解读：七步构建玩具视频编码器

> 原文：skywind《视频编码原理简介》 https://skywind.me/blog/archives/1566
> 本文按原文的七个步骤逐一拆解：每步做什么、为什么这么做、关键数字与公式，并补充直觉解释。

---

## 第一步：有损图像压缩（先学会压一张图）

视频是连续的图，所以第一步先解决"压一张图"——本质上是手写一个迷你 JPEG。

### 1.1 RGB → YUV

把每个像素从 RGB 转成 YUV：Y 是亮度（黑白电视看到的那部分），U/V 是色度（颜色偏移量）。转换只是三行线性公式。

为什么要转？因为**人眼对亮度敏感、对颜色迟钝**——所以后续可以对 U/V 下狠手（粗量化、降采样）而画面看起来没差多少。转完之后把 Y、U、V 当成三张独立的灰度图分别处理。

### 1.2 8×8 分块 + DCT 变换

把每张灰度图切成 8×8 的小块，每块做 DCT（离散余弦变换，Discrete Cosine Transform）。

直觉：DCT 把 64 个像素值换算成 64 个"频率配方"系数——左上角的低频系数描述这块的大致明暗轮廓，右下角的高频系数描述细小纹理。自然图像的能量绝大部分集中在低频，也就是说**变换之后，重要信息挤在左上角，右下角基本是接近零的小数**。

### 1.3 量化（有损发生在这里）

量化（quantization）就是"除以步长再取整"，是整条链路里**唯一真正丢信息**的环节：

- 左上角低频：步长取 1，数据 0~255 全保留；
- 右下角高频：步长可取 10，除以 10 后小数丢掉。

原文的描述：量化之后，左上角的数据由于步长小、依然比较离散，而右下角的高频数据变得很统一，**往往是一长串 0**。这正是为下一步压缩铺路——把数据"揉"成重复度高的形状。

### 1.4 熵编码（原文的作弊点：直接用 LZMA2）

JPEG 标准用 RLE（游程编码）+ Huffman 来压这 64 个字节；原文直接建议**调现成的 LZMA2 库**。效果一样是无损压缩掉那串 0，但省去了自己写熵编码器的大量工作。

### 1.5 去块滤波（de-block）

8×8 独立处理会在块边界留下"马赛克接缝"。最简化的处理（原文原话）："边界部分几个像素点和周围插值模糊一下"。

> 至此你有了一个完整的有损图像编解码器。视频里的 I 帧（关键帧）就是用它压出来的。

---

## 第二步：宏块误差计算（学会判断"两块图像像不像"）

视频压缩的单位比 8×8 更大：**16×16 的宏块（macroblock）**。

像素坐标 → 宏块坐标的换算：

```
s = x / 16 = x >> 4
t = y / 16 = y >> 4
```

两个宏块的相似度用平方误差和衡量：

```
PixelDiff(c1, c2) = (c1 - c2)²
BlockDiff(b1, b2) = Σ PixelDiff      // 16×16 = 256 个像素求和
```

直觉：把 16×16 宏块拉直成一个 256 维向量，BlockDiff 就是两个向量的欧氏距离平方。距离小 = 两块长得像。这一步只是个工具函数，给第三步用。

---

## 第三步：运动预测（视频压缩真正的魔法）

相邻两帧 P1、P2 通常只是"画面里的东西挪了挪"。于是对 P2 的每个宏块，去 P1 里找一个最像它的 16×16 区域：

- 搜索方式（原文）：以 P2 中该宏块的对应坐标为中心，在 P1 中**向四周慢慢扩散**，搜索一定步长范围——不需要暴力遍历整帧。
- 找到后记下那个区域的左上角坐标 (x, y)。

全帧搜完，得到一串坐标对——这就是**运动矢量（motion vector）**。规模感受（原文例子）：VCD 分辨率 352×240，横向 22 块 × 纵向 15 块 = **330 个坐标对**就能描述"这一帧大致怎么从上一帧挪出来"。

直觉：与其重新画一张图，不如发一张"挪动说明书"：第 3 行第 5 块？从上一帧 (51, 80) 那里抠过来贴上。按说明书从 P1 拼出来的帧记作 **P2′（预测帧）**。

---

## 第四步：P 帧编码（挪动说明书 + 补丁图）

P2′ 毕竟是拼出来的，和真实的 P2 有误差。把误差也编进去：

```
D2 = (P2 - P2′) / 2
```

- 差值范围是 [-255, 255]，超出一个字节。原文的处理：**除以 2**，用 8 位表示 [-254, 254]，精度牺牲到 2；
- 再 **+0x80** 整体偏移，让 128 代表 0、129 代表 +2、127 代表 -2，绕开符号问题。

D2 这张"补丁图"本身信息量很低（大部分地方接近 0），所以用**更粗的量化、16×16 的块**做有损编码就够了——原文：可以理解成"用质量更低的 JPEG 编码"。

最终一个 P 帧 = 挪动说明书 + 补丁图：

```
Encode(P2) = Lzma2(330 个块坐标) + 有损编码(D2)
```

这就是 P 帧比 I 帧小一个数量级的原因。

---

## 第五步：GOP 生成（把帧串成可播放的序列）

三种帧：

- **I 帧**：不依赖任何帧，独立解码（就是第一步的产物）；
- **P 帧**：参考前面一帧（第四步的产物）；
- **B 帧**：参考前后两帧（如参考 P1 和 P3 编出 P2，间隔不一定是 1）。

一个 **GOP（Group of Pictures）** = 一个 I 帧开头 + 一串 P/B 帧，例如：

```
I, P, B, B, P, B, B, P, B, B, P
```

### 误差累积与参考帧策略

P 帧逐帧链式参考（P2 参考 P1，P3 参考 P2……）会让有损误差一层层叠上去，到 GOP 后期画质明显劣化。原文给的两种缓解：

1. P1~P9 **全部直接参考 I1**；
2. 或分段：P1~P4 参考 I1，P5~P9 参考 P5——原文："这样步子小点，误差也不算太离谱"。

### 播放约束

原文点出一个流媒体常识的根源："只有完整收到下一个 GOP 的 I 帧才能开始播放"——这就是为什么直播秒开、seek 落点都绕不开关键帧。

---

## 第六步：容器组装（给数据装盒贴标签）

裸的帧数据流没法用，需要一个文件格式记录元数据：**分辨率、帧率、时间索引**等——原文："类似 MP4（h.264 的容器）"。自己定义一个简单的二进制格式即可。

配套写个播放器验证：解码 + SDL/DirectX/OpenGL 上屏。

---

## 第七步：优化改进（分水岭，原文也建议点到为止）

两大方向：

1. **编码效率**：同等质量下码率更低；
2. **编码性能**：同等质量和码率下速度更快。

原文给的学习路径：玩具做完后回头读 JPEG、MPEG-1/2 标准和实现代码——"你会发现简单很多了"；再针对性看 H.264 的 I 帧编码和各种搜索预测方法；有了 H.264 基础，HEVC 和 vpx 系就容易理解了。

实践态度（原文）："可以侧重原理，各种优化技巧了解下即可，本来就是 hack 性质的"。这些知识的最终价值：将来**需要使用并修改真实编码器、为它们增加新特性**的时候用得上。
